# 개발 문서 안내

서비스가 무엇을 해야 하는지는 `product/`, 개별 이슈를 어떻게 구현할지는 `plans/`, 여러 이슈에 걸쳐 지켜야 하는 기술 결정은 `decisions/`, 화면 디자인 시안과 채택 범위는 `design/`, 외부 서비스 설정 같은 운영 절차는 `ops/`에서 관리한다.

## 먼저 읽을 문서

| 문서 | 답하는 질문 |
| --- | --- |
| [서비스 기획](product/overview.md) | 누구의 어떤 문제를 풀고, 어디까지 만드는가? |
| [요구사항](product/requirements.md) | 사용자가 무엇을 할 수 있고, 어떤 결과면 완료인가? |
| [외부 데이터](product/data-source.md) | 공공 API로 무엇을 알 수 있고, 무엇을 직접 확인해야 하는가? |
| [개발 순서와 결정할 사항](product/development.md) | 다음 작업은 무엇이고, 무엇을 결정해야 하는가? |

## 문서 사용 방법

1. `product/`의 초안을 검토해 이번에 만들 범위와 미정 사항을 결정한다.
2. 작업을 이슈로 나눌 때 요구사항 ID와 해당 완료 조건을 가져온다.
3. 선행 이슈가 머지된 뒤 `plans/<이슈번호>-<슬러그>.md`를 작성한다. 형식은 기존 플랜 규칙을 따른다.
4. 제품 동작이 바뀌면 요구사항을, 구현 방법이 바뀌면 해당 이슈 플랜을 고친다. 과거 플랜을 현재 제품 명세처럼 덮어쓰지 않는다. 여러 이슈에 걸치는 기술 결정이 바뀌면 기존 결정 문서를 고치지 않고 새 결정 문서로 대체한다.
5. 완료 여부는 이슈·PR·검증 결과로 추적한다. 제품 문서의 ‘제안’을 ‘구현 완료’로 읽지 않는다.

예: `REQ-SAVE-01 관심 정책 저장` → 이슈에 중복 저장·사용자 분리 완료 조건 기재 → 구현 플랜에 DB 제약·인증 검사·테스트를 구체화한다.

요구사항 ID는 한번 사용하면 유지한다. 범위를 빼면 ID를 재사용하지 않고 제외 이유를 남긴다. ERD와 서버 API 명세는 데이터 검증과 첫 기능 설계 시 추가하고, 지금부터 미확정 스키마를 별도 문서들에 중복 관리하지 않는다.

저장소 작업 방식과 검증 규칙은 [AGENTS.md](../AGENTS.md)를 따른다.

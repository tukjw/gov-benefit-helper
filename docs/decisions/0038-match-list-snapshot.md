# 0038. 조건 비교 목록의 메모리 판정 입력

- 상태: 채택
- 날짜: 2026-11-01
- 출처: #98, [플랜](../plans/98-guest-match-throughput.md)

## 배경

조건 비교 목록(`POST /api/matches`, `GET /api/me/matches`)은 요청마다 혜택 1.1만 건과 지원조건 원문 1.1만 건을 DB에서 읽고, 원문을 JSON으로 파싱한 뒤 판정했다. #96 기준 측정에서 이 경로는 초당 7\~8건에서 한계에 걸렸다. 요청 1건에 DB에서 약 25MB를 받았고, 판정하는 동안 커넥션을 쥐어 혼합 시나리오의 검색·상세까지 느려졌다. 로컬에서 나눠 보니 요청 스레드 CPU의 3분의 2가 지원조건 원문 파싱이었고, 요청 1건이 약 335MB를 할당했다([보고서](../research/guest-match-throughput.md)).

판정 결과는 프로필마다 다르지만, 판정에 쓰는 혜택 쪽 값(목록 항목, 사용자구분, 운영 기관 지역, 지원조건 코드)은 프로필과 무관하고 수집으로만 바뀐다. 이 결정은 그 값을 어디에 두고 언제 바꾸는지 정한다.

## 결정

- 조건 비교 목록은 혜택마다 목록 항목(`BenefitSummary`), 사용자구분, 운영 기관 지역, 파싱한 지원조건을 담은 목록을 앱 메모리에 두고 판정한다(`MatchCandidateStore`). 순서는 검색과 같은 DB 정렬 순서다. 프로필, 나이, 판정 결과는 담지 않는다.
- 목록은 수집 실행이 끝날 때마다(성공·부분 실패·실패 모두) 새로 만들어 바꾼다. 수집은 끝날 때 `CollectionRunFinished`를 낸다.
- 비어 있으면(기동 직후, 교체 실패 뒤) 첫 요청이 DB에서 만들고, 동시에 온 요청은 기다린다. 만들기와 바꾸기는 한 잠금 안에서 한다.
- 교체에 실패하면 비우고 예외를 수집 쪽으로 그대로 던진다. 다음 요청이 다시 만든다.
- 만료 시간, 버전 확인, 끄는 설정은 두지 않는다.
- 그래서 목록은 마지막으로 끝난 수집 기준이고, 수집이 도는 동안부터 교체가 끝날 때까지는 직전 수집 기준이다(`DEC-FRESHNESS`). 상세 비교·검색·상세는 지금처럼 요청마다 DB를 읽는다.
- 목록 판정은 트랜잭션 밖에서 해 커넥션을 쥐지 않는다.

## 근거

- 혜택과 지원조건을 쓰는 곳은 수집(`CollectionPageWriter`)뿐이고 수집은 하루 한 번이다. 바뀌는 시점이 하나라 만료 시간 없이 수집이 끝날 때 바꾸면 된다. 로컬 전체 수집은 37.6초였다.
- 수집은 쪽마다 커밋한다. 요청마다 읽던 방식도 수집 중에는 반쯤 바뀐 데이터를 읽었다. 직전 수집 기준을 유지하는 편이 오히려 일관된다. 실패한 실행도 저장한 쪽이 있을 수 있어 상태와 관계없이 바꾼다.
- 만드는 쿼리와 파싱은 요청마다 하던 것을 그대로 옮겼고, 판정은 같은 `ConditionMatcher`다. 실행 시점만 바뀌므로 수집과 수집 사이의 결과(건수·판정·순서)가 같다. 순서를 메모리에서 다시 정렬하지 않으므로 콜레이션 차이도 생기지 않는다.
- 한 잠금으로 만들기와 바꾸기를 줄 세우는 이유: 수집 중에 비어 있는 목록을 채우기 시작한 요청이 수집 뒤의 교체보다 늦게 끝나면, 수집 전 데이터로 덮어 다음 수집까지 남는다(`REQ-QUALITY-02`). 잠금 안에서 기다린 교체가 그 뒤에 돌아 덮는다.
- 메모리에 두는 이유: 운영은 앱 하나다([결정 0037](0037-proxmox-deploy-metrics-and-load-test.md)). 정기 수집(`CollectionScheduler`)과 로그인 시도 제한([결정 0035](0035-login-attempt-limit.md))도 같은 전제다. 크기는 1.1만 건에 수십 MB 이하다.
- 결정 0008의 "지원조건 코드는 원문으로만 둔다"는 DB 저장 규칙이다. 이 목록은 DB에 저장하지 않으므로 0008을 대체하지 않는다.
- 제외한 대안
  - 필요한 컬럼만 읽기: 로컬에서 요청 1건당 CPU가 약 34% 줄었지만 지원조건 원문 읽기·파싱이 남고, 요청마다 1.1만 행을 읽고 정렬한다.
  - 수집 때 비교 코드를 컬럼으로 저장: 0008을 대체하고 기존 행을 채워야 하며, 요청마다 1.1만 행을 읽는 비용은 남는다.
  - 판정·정렬을 SQL로: 판정 로직이 Java(상세)와 SQL(목록) 두 벌이 된다.
  - 프로필 값별 결과 캐시: 생년월일·거주지·속성 조합이라 사람 사이 적중률이 낮다.
  - 만료 시간(TTL): 데이터가 수집으로만 바뀌어 같은 것을 다시 만드는 낭비이고, 허용 지연 수치를 따로 정해야 한다.

## 적용 위치

- `backend/src/main/java/kr/govbenefit/match/service/MatchCandidateStore.java`: 목록 보관, 비었을 때 만들기, 수집 뒤 교체
- `backend/src/main/java/kr/govbenefit/match/service/MatchCandidateLoader.java`, `MatchCandidate.java`: DB에서 만드는 쿼리와 담는 값
- `backend/src/main/java/kr/govbenefit/collection/service/CollectionService.java`, `collection/domain/CollectionRunFinished.java`: 수집 종료 이벤트
- `backend/src/main/java/kr/govbenefit/match/service/MatchService.java`: 목록 판정, 트랜잭션 밖 실행
- `backend/src/test/java/kr/govbenefit/MatchCandidateResetListener.java`: 테스트 메서드마다 비우기

## 영향

- 혜택이나 지원조건을 바꾸는 새 경로(수동 수집, 관리 기능 등)는 끝날 때 `CollectionRunFinished`를 내거나 교체를 일으켜야 한다.
- 목록 항목이나 판정에 혜택 쪽 값을 더하면 `MatchCandidate`에도 더한다.
- 앱을 여러 대로 늘리면 인스턴스마다 교체 신호가 필요하다. 그때 이 결정을 대체한다.
- 테스트는 데이터를 수집으로 넣으면 교체가 따라온다. DB를 직접 고치는 테스트는 교체를 직접 일으킨다.

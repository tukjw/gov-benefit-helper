# 0021. 거주 지역 코드

- 상태: 채택
- 날짜: 2026-10-17
- 출처: #49, [플랜](../plans/49-user-profile.md)

## 배경

#49에서 프로필의 거주 시도·시군구를 받으면서 지역을 어떤 값으로 식별할지 정해야 했다. `DEC-PROFILE`에서 거주 지역은 운영 기관 지역 필터(`REQ-SEARCH-01` P1)의 기본값에만 쓰고 조건 비교에는 쓰지 않는다. 지역 필터는 혜택의 운영 기관과 비교하므로, 프로필 값과 혜택 데이터가 같은 체계여야 매핑이 필요 없다. 공공서비스 API에는 대상 지역 필드가 없고 소관기관명·소관기관코드만 있다([보고서 §7](../research/gov24-api-data.md#7-대상-지역을-판별할-근거)).

## 결정

거주 지역은 **행정표준기관코드**(7자리)로 식별한다. 공공서비스 API 목록의 `소관기관코드`(`benefit.agency_code`)와 같은 값이다.

- 기준 테이블 `region`(`code`, `name`, `parent_code`, `display_order`)에 시도 16개와 자치 시군구 227개를 둔다. 2026-10-01 수집분의 소관기관유형 `광역시도`·`시군구`에서 뽑아 마이그레이션(`V8__create_region.sql`)으로 고정한다. 수집 결과가 바뀌어도 이 표는 따라 바뀌지 않는다.
- 일반구는 두지 않는다. 세종(`5690000`)과 제주(`6500000`)는 시군구가 없다.
- 시군구 코드는 시도 코드를 포함하지 않으므로 소속은 `parent_code`로만 안다.
- 시군구 이름은 기관명에서 시도명을 뗀 값(`강남구`)이다. 시도 순서는 관례 순서(서울 → 제주), 시군구 순서는 같은 시도 안에서 코드 오름차순이다.
- 프로필은 시도만 입력할 수 있다. 시군구는 시도와 함께, 그 시도의 시군구만 받는다.
- 행정구역 개편으로 폐지된 코드의 처리는 정하지 않았다. 폐지 표시 컬럼도 두지 않는다.

## 근거

- 2026-10-17에 실제 API를 호출해 `소관기관코드`가 7자리 행정표준기관코드임을 확인했다(종로구시설관리공단 `3000000`, 전남광주통합특별시 동구 `5805000`, 양산시인재육성장학재단 `5380000`). 수집은 이 값을 가공하지 않으며, 원문(`source_record`)과 `agency_code`가 다른 행은 0건이었다.
- 2026-10-01 수집분에서 광역시도는 16개 코드·16개 이름, 시군구는 227개 코드·227개 이름이고 코드가 없는 행은 없었다. 시군구 이름은 모두 `<시도명> <시군구명>`이고 시도명은 모두 광역시도 16개 중 하나였다. 2026년 개편(광주·전남 통합, 인천 구 개편)이 반영돼 있다.
- 지방공기업 561건과 지방출자·출연기관 580건의 `agency_code`가 모두 시도나 시군구 코드와 같았다. 산하 기관이 상위 자치단체 코드를 쓰므로 이름에 시도가 없는 기관(`강북구도시관리공단` 등)도 코드로 지역을 정할 수 있다.
- 수원·창원 혜택은 `경기도 수원시`처럼 시 단위로만 나오고, 제주는 시군구 혜택이 없었다(제주시·서귀포시는 행정시). 받아도 쓸 곳이 없는 단위는 두지 않았다.
- 대안: 법정동코드(5자리). 주소 체계의 표준이지만 기관코드와의 매핑을 따로 만들어야 하고, 개편이 반영된 원본 파일을 따로 받아야 한다.
- 대안: 정적 enum·JSON. 개편 때 재배포가 필요하고 DB가 저장값을 검증하지 못한다.
- 대안: 수집할 때마다 목록을 만듦. 수집 결과에 따라 목록이 흔들려 입력 검증 기준이 될 수 없다.
- 한계: 개편하면 기관코드가 바뀐다. 전남광주통합특별시 동구 혜택의 서비스ID는 통합 전 코드로 보이는 `359…`로 시작하지만 소관기관코드는 `5805000`이다. 개편 전에 저장한 프로필의 코드는 낡을 수 있다.

## 적용 위치

- `backend/src/main/resources/db/migration/V8__create_region.sql`: 기준 테이블과 시드
- `backend/src/main/resources/db/migration/V9__create_user_profile.sql`: `user_profile.sido_code`·`sigungu_code`의 FK
- `backend/src/main/java/kr/govbenefit/region/`: `Region`, `RegionRepository`
- `backend/src/main/java/kr/govbenefit/profile/service/ProfileValidator.java`: 시도·시군구 검증
- `backend/src/main/java/kr/govbenefit/profile/service/ProfileService.java`: 선택지 API(`GET /api/me/profile/options`)의 지역 목록
- `backend/src/test/java/kr/govbenefit/region/repository/RegionSeedTest.java`

## 영향

- 운영 기관 지역 필터(`REQ-SEARCH-01` P1)는 `region`과 `benefit.agency_code`로 프로필의 기본값을 정한다. 기관명을 해석하지 않는다.
- 행정구역이 개편되면 새 코드 시드와 기존 프로필의 코드 처리를 한 마이그레이션 이슈로 다룬다.
- 주소 검색 등 주소 기반 기능을 붙이면 법정동코드와의 매핑을 다시 검토한다.
- 지역 목록이 공개 API로 필요해지면(지역 필터 등) 그때 별도 경로로 나누고 [0018](0018-api-auth-boundary.md)의 공개 경로 기준을 따른다.

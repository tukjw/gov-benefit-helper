# 배포 때 새 혜택 알림 발송 종료 처리 개선 측정 (#141)

새 혜택 알림을 보내는 중에 배포해도 같은 알림이 두 번 나가지 않도록 발송 종료 처리를 고치고, #137의 `deploy` 시나리오를 운영 VM에서 같은 조건으로 다시 쟀다. [측정 기록 형식](../product/development.md#측정-기록-형식)을 따른다. 구현 계획은 [`docs/plans/141-notify-send-graceful-shutdown.md`](../plans/141-notify-send-graceful-shutdown.md), 결정은 [0049](../decisions/0049-new-benefit-digest-send-shutdown.md), 기준값은 [알림 발송 장애 기준 측정](notify-send-fault-baseline.md)(#137) 5.3절, 원본 결과는 `docs/research/notify-send-graceful-shutdown/results/20261111T161652-deploy/`에 있다.

## 요약

- **발송 중 배포 3번에서 중복 접수가 3건에서 0건이 됐다.** 못 받은 묶음, 끝나지 않은 묶음, 최종 실패도 모두 0이다.
- **이전 앱은 종료 신호를 받고 0.2\~0.3초 안에 발송을 멈췄다.** 회차마다 `interrupted=true` 발송 요약 로그를 명령 0.36\~0.45초 뒤에 남겼다. #137에서는 30초 동안 계속 보냈고 요약 로그가 없었다.
- **배포 명령에서 다시 UP까지 약 40초에서 약 9초로, 발송 재개까지 약 60초에서 약 30초로 줄었다.** 이전 앱이 종료 대기 30초를 다 쓰지 않고 끝나기 때문이다.
- 발송이 실제로 끊긴 시간은 회차마다 약 29초로 #137과 같다. 남은 시간은 새 앱 기동(약 9초)과 다음 30초 cron까지의 대기다.
- 총 소요는 1,695.7초로 #137보다 31초 길다. 배포 때문이 아니다. 첫 배포 전 구간부터 요청 한 건당 앱 처리 시간이 평균 3ms 길었다(5절).

## 1. 사용자에게 생기는 문제와 재현 조건

- 문제: 발송 중에 배포하면 배포 한 번마다 한 명이 같은 알림을 두 번 받는다. 1만 통을 보내는 실행 한 번이 약 26분이라, 발송 시간대에 배포하면 매번 생긴다.
- 원인(#137 5.3절, 결정 0049)
  - 종료가 시작돼도 Spring 스케줄러는 새 실행만 막고, 실행 중인 발송은 30초까지 기다린다. 발송 루프에는 신호가 가지 않는다.
  - 30초가 지나면 발송이 계속되는 채로 JPA와 커넥션 풀이 닫히고 JVM이 끝난다. 그때 보내던 묶음은 SES가 접수했지만 `PENDING`으로 남아 새 앱이 다시 보낸다.
- 재현: #137의 `deploy` 시나리오. 1만 통을 보내는 동안 5분·12분·19분에 같은 이미지로 app만 다시 만든다(`docker compose up -d --force-recreate app`).

## 5. 개선과 같은 조건의 결과

### 비교한 대안

플랜의 설계 결정과 결정 0049에 있다. 종료 이벤트(`ContextClosedEvent`)를 받아 발송 루프가 묶음마다 확인하고 멈추는 방식을 골랐다. 스케줄러 종료 설정, 한 실행이 보내는 양 제한, 전용 스레드, 점유 상태, 배포 절차에서 일시정지는 단독으로 이 문제를 풀지 못하거나 이슈가 제외한 범위다.

## 6. 정합성과 한계

### 정합성

- 실제 SES로 나간 요청이 없다.
  - 측정용 실행 구성은 SES 주소를 가짜 SES로 돌리고 가짜 접근 키를 넣는다. `run.sh`가 시작 전에 앱 환경 변수를 확인했고, `switch.sh on`이 합성 묶음 1건을 가짜 SES가 접수하는지 보고 시작했다.
  - 묶음의 `ACCEPTED` 수(10,000)와 가짜 SES가 접수한 수신 주소 수가 같다(조용한 유실 0).
  - 측정 뒤 CloudWatch(서울 리전) `AWS/SES`의 `Send`에서 16:10\~16:50 KST에 실제로 나간 메일은 0통이었다(사용자 확인).
- 정리 결과
  - 측정이 끝난 뒤 합성 사용자·묶음·가짜 새 혜택·계정 메일 인증 기록이 모두 0건이었다(`cleanup.txt`).
  - `switch.sh off`가 기본 실행 구성으로 app을 다시 만들고, 실행 구성 파일 해시와 `APP_TAG`가 측정 전과 같다고 확인했다. Tunnel을 다시 켰다.
  - 측정 뒤 `scripts/deploy.sh v0.1.5`로 되돌렸다. app VM의 `APP_TAG`는 `v0.1.5`다.
- 테스트(`NewBenefitDigestSendTest`)
  - 발송 중 종료 이벤트를 받으면 보내던 묶음은 `ACCEPTED`로 기록되고, 다음 묶음은 `PENDING`으로 남아 다음 실행이 보낸다. 요약 로그는 `interrupted=true`다.
  - 다른 컨텍스트(관리 포트의 자식 컨텍스트)가 닫힐 때는 멈추지 않는다.
- 로컬 리허설(2026-11-11 15:55, 내 PC, 사용자 1,000명, 0.5·1.5·2.5분에 배포 3번): 중복 0, 중단 3, 명령 → 멈춤 요약 로그 0.13\~0.58초였다. 원본 결과는 저장소에 두지 않는다.

### 한계

- 강제 종료(SIGKILL)와 응답 유실에서 생기는 중복은 그대로다(결정 0048이 받아들인 한계, #137 5.1·5.2절).
- 보내던 한 건이 끝나는 데 30초를 넘기면(SES 연결·응답 제한은 합쳐 15초이므로, DB 기록이 멈춘 경우 등) 지금처럼 끊길 수 있다. 이번 측정에서는 보내던 한 건이 0.4초 안에 끝났고, SES 응답이 늦는 경우는 재지 않았다.
- `deploy` 시나리오 한 번만 쟀다. 다른 시나리오는 이 변경과 관계가 없어 다시 재지 않았다.
- 실제 배포(`scripts/deploy.sh`)는 이미지를 받은 뒤 같은 방식(`docker compose up -d`)으로 app을 다시 만들어, 측정의 `--force-recreate`와 종료 순서가 같다. `scripts/deploy.sh`로 바꾸는 것은 따로 재지 않았다.

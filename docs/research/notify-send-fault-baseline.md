# 알림 발송 장애 기준 측정 (#137)

운영 앱이 새 혜택 알림 1만 통을 보내는 동안 장애를 주입해 유실, 중복 접수, 끝나지 않은 묶음, 최종 실패, 복구 시간의 기준값을 [측정 기록 형식](../product/development.md#측정-기록-형식)에 맞춰 남긴다. 구현 계획은 [`docs/plans/137-notify-send-fault-baseline.md`](../plans/137-notify-send-fault-baseline.md), 재현 스크립트는 `scripts/loadtest/notify/`, 절차는 [부하 테스트](../ops/load-test.md#알림-발송-장애-측정), 원본 결과는 `docs/research/notify-send-fault-baseline/results/`에 있다. 확인한 문제의 개선은 다루지 않는다(7절의 후속 이슈 후보).

## 1. 요약

- 8개 시나리오 모두 **못 받은 묶음 0, 끝나지 않은 묶음 0, 최종 실패 0**이다. 1시간 SES 장애에서도 1만 통이 모두 그날 기한 안에 접수됐다.
- **중복 접수는 앱이 SES 접수 뒤 기록 전에 끝날 때마다 1건씩 생긴다.** 강제 종료 10번에 10건, 배포 3번에 3건, 응답 유실 101번에 101건이다.
- **배포는 매번 보내던 묶음 1건을 중복으로 보낸다.** 종료 신호를 받은 앱이 30초 동안 계속 보내다 발송 도중에 끝나기 때문이다. 배포 명령에서 발송 재개까지 약 60초다.
- **발송 속도는 초당 6.49건이다.** 결정 0048이 가정한 초당 10건의 65%다. 1만 통에 25.7분이고, 10만 통이면 약 4.3시간이 걸린다. 한 건씩 차례로 보내므로 SES 응답 시간(평균 136ms)이 속도를 정한다.
- **한 번의 발송 실행이 공용 스케줄러 스레드를 끝날 때까지 붙잡는다.** 1만 통이면 26분, 응답 유실이 섞이면 42분이다. 그동안 15분마다 도는 다른 예약 작업이 실행되지 못했고, 1분 뒤 재시도도 실제로는 실행이 끝난 뒤(26분 뒤)에 나갔다.
- 1시간 장애가 끝난 뒤 6,544건은 17분 안에 접수됐다. 장애 동안 세 번 실패한 3,456건은 30분 재시도 대기에 걸려 21\~32분 뒤에 접수됐다.
- **10만 통은 SES 하루 할당량(24시간에 5만 통)을 넘는다.**
- 알림과 계정 메일이 함께 초당 한도를 넘으면 계정 메일이 실패한다. 계정 메일이 초당 10건으로 몰린 2분 동안 인증번호 메일 79건이 실패했다. 계정 메일은 다시 보내지 않는다.
- 알림을 끈 사용자에게 끈 뒤 나간 알림은 0건이다.

## 2. 측정 대상과 재현 조건

- 사용자에게 생기는 문제
  - 같은 알림 메일을 두 번 받는다(앱이 SES 접수 뒤 결과를 기록하기 전에 끝나거나 응답을 잃을 때).
  - 알림을 늦게 받는다. 발송이 느리거나 SES 장애 뒤 재시도가 밀릴 때다.
  - 알림을 보내는 동안 가입 인증번호 메일을 받지 못한다(SES 초당 한도 초과).
- 측정 일시
  - 전체 측정 `run.sh all`: 2026-11-11(수) 00:41\~06:14 KST
  - 실제 SES 사전 측정(app VM): 2026-11-10 00:58 KST
- 실행: 부하 생성 VM의 `tmux`에서 커밋 `31da703`으로 실행했다. 8개 시나리오를 한 번에 이어서 쟀다.
- 이 보고서의 값은 모두 2026-11-11 측정이다. 2026-11-10에 한 번 쟀지만 측정 도구가 요청마다 약 41ms를 더해 다시 쟀다. 달라진 값은 6절에 있다.
- 측정하는 동안 Tunnel을 멈춰 API를 막았다. 운영에는 아직 실제 사용자가 없다.
- 원본 결과
  - `results/20261111T004126-all/<시나리오>/`: 전체 측정. `finish.txt`(정리 결과)와 `run.log`가 함께 있다.
  - `results/ses-probe/`: 실제 SES 사전 측정(내 PC 2026-11-09, app VM 2026-11-10)과 가짜 SES 지연 표본 `latency-ms.txt`
  - 시나리오마다 `meta.json`(시나리오 값, 이미지 태그, 실행 구성 해시, 커밋, 시각), `fake-ses.jsonl.gz`(가짜 SES가 받은 요청 전체), `digests.tsv`(끝났을 때 묶음 상태), `injections.tsv`(주입 시각), `app-log.txt.gz`, `prometheus.json`, `counts.json`·`counts.txt`(집계)를 둔다. 파일 설명은 [부하 테스트](../ops/load-test.md#끝난-뒤)에 있다.
- 다시 셀 때: `python3 scripts/loadtest/notify/count.py <결과 디렉터리>`

## 3. 데이터와 실행 환경

- 규모 가정: **사용자 10만 명 중 1만 명이 같은 날 알림을 받는 날**이다. 알림은 기본으로 꺼져 있고, 혜택의 대부분은 지자체·지방 기관 혜택이라 그 지역 주민에게만 '해당'이 된다([데이터 검증 보고서](gov24-api-data.md) §7). 10만 명이 모두 받는 날은 잰 처리량으로 환산했다(5.6절).
- 합성 데이터(운영 DB, 시나리오마다 넣고 지움)
  - 사용자 1만 명(`notify-00001@loadtest.invalid` \~ `notify-10000@loadtest.invalid`), 알림 켬, 로그인할 수 없는 비밀번호 값
  - 사용자마다 그날 발송 대기 묶음 하나. 묶음마다 가짜 새 혜택 3건을 담는다.
  - 가짜 새 혜택 3건: `new_benefit`에 없는 실제 혜택 중 ID 순 앞 3건으로 만들었다. 메일 본문은 실제 혜택 이름으로 만들어진다.
- 앱
  - 이미지 `v0.1.5`. 운영 실행 구성(`compose.yaml`)에 측정용 덮어쓰기 파일 `compose.notify-fault.yaml`을 더했다.
  - 덮어쓰기는 SES 주소를 가짜 SES(`http://10.10.0.14:8025`)로 돌리고, 가짜 접근 키를 넣고, 수집·묶기·인증 기록 파기를 끈다.
  - `app.env`는 고치지 않았다.
  - 발송 구조(결정 0048): 30초 cron, 공용 스케줄러 스레드 하나, SES 호출 사이 최소 100ms, SDK 재시도 없음, 응답 제한 10초. 재시도 간격은 1분·5분·30분·2시간·6시간이고 묶은 날 24:00(KST)까지만 보낸다.
  - 강제 종료와 배포 뒤 Docker가 다시 띄운다(`restart: unless-stopped`).
- VM: [부하 테스트 기준 측정](load-test-baseline.md#2-데이터와-실행-환경)과 같다(app 4 vCPU, db 2 vCPU, 부하 생성 2 vCPU, 한 호스트의 내부 브리지).
- 가짜 SES(`fake_ses.py`, 부하 생성 VM)
  - 응답 지연: app VM에서 실제 SES에 차례로 보낸 100건의 성공 지연에서 무작위로 고른다(시드 고정). p50 92.0ms, 평균 134.8ms다.
  - 속도 제한: 초당 14건이 차는 토큰 버킷(용량 145건). 넘으면 `429 TooManyRequestsException`으로 응답한다.
  - 받은 요청을 모두 수신 주소·도착 시각·응답 시각·결과와 함께 기록한다. 유실과 중복은 앱 DB가 아니라 이 기록으로 센다.
  - 응답은 헤더와 본문을 한 번에, 곧바로 보낸다(`TCP_NODELAY`). 고른 지연 말고 더하는 시간이 없게 하기 위해서다(6절).

### 실제 SES 사전 측정

가짜 SES의 지연과 속도 제한의 근거다. 메일박스 시뮬레이터(`success@simulator.amazonses.com`)로만 보냈고, 앱과 같은 SDK와 클라이언트 설정을 썼다.

| 측정 | 내 PC(2026-11-09) | app VM(2026-11-10) |
| --- | --- | --- |
| 차례로 100건(초당 5건) | 첫 요청 360.4ms, p50 131.5, p90 207.1, p99 223.2ms | 첫 요청 582.1ms, p50 92.0, p90 245.8, p99 284.8ms, 평균 134.8ms |
| 동시 12개로 60건 | 0.58초에 모두 성공(초당 약 103건) | 하지 않음 |
| 초당 30건으로 20초 | 9.05초까지 272건 성공, 그 뒤 188건이 `429 TooManyRequestsException` | 하지 않음 |

- 초당 한도를 넘으면 버킷 용량 약 145건을 쓴 뒤 429를 받는다. 앱은 429를 일시 실패로 분류한다.
- app VM의 p50이 내 PC보다 30% 낮아, 가짜 SES 지연 표본을 app VM 값으로 바꿨다.
- 계정 한도(SES 콘솔 Account dashboard, 서울 리전): **하루 5만 통(24시간), 초당 14통**이다.

## 4. 요청 분포와 실행 방식

모든 시나리오는 1만 통이다. 시각은 발송 시작(가짜 SES가 첫 알림 요청을 받은 때) 기준이다.

| 시나리오 | 주입 |
| --- | --- |
| `outage-1h` | 0\~60분 동안 모든 요청에 `500 InternalFailure` |
| `normal` | 없음 |
| `kill` | 90\~150초 무작위 간격(시드 고정)으로 10번 SIGKILL. 간격은 앞 회차에서 발송이 다시 시작된 때부터 잰다. 8·9회차는 가짜 SES가 요청을 접수한 채 붙잡고 있는 동안 죽인다(SES 접수 뒤 기록 전 종료를 일부러 재현) |
| `deploy` | 5분·12분·19분에 같은 이미지로 app만 다시 만든다(`docker compose up -d --force-recreate app`, 종료 신호 → 30초 대기 → 종료) |
| `response-loss` | 100번째 요청마다 접수하고 15초 뒤에 응답한다. 앱의 응답 제한(10초)보다 길다 |
| `outage-10m` | 0\~10분 동안 `500 InternalFailure` |
| `account-mail` | 30분 동안 가입 인증번호 요청을 초당 1건, 5\~7분에는 초당 10건 보낸다(k6, 요청마다 다른 이메일) |
| `notify-off` | 1,000명(시드 고정)의 알림을 0\~20분 사이 무작위 시각 100번에 나눠 DB에서 끈다 |

- 시나리오는 합성 묶음에 `PENDING`이 없고 가짜 SES가 2분 동안 요청을 받지 않으면 끝난다. 모든 시나리오가 이 조건으로 끝났다(시간 초과 없음).
- 센 값
  - 접수: 가짜 SES가 받아들인 요청. 늦은 응답(`accepted_late`)과 붙잡힌 채 앱이 죽은 요청(`accepted_held`)도 접수다.
  - 못 받은 묶음(유실): 취소되지 않은 합성 묶음 중 접수가 0번인 것. 묶음 상태가 `ACCEPTED`인데 접수가 0번이면 조용한 유실이다.
  - 중복 접수: 같은 수신 주소의 두 번째 이후 접수.
  - 끝나지 않은 묶음: 측정 끝에 `PENDING`. 최종 실패: `FAILED`.
  - 재개 시간: 강제 종료·배포 명령 뒤 알림 요청이 3초 이상 끊긴 구간이다. 이전 앱이 끝난 뒤(명령이 끝난 뒤) 다시 온 첫 요청을 재개로 본다.
  - 총 소요: 첫 요청부터 마지막 접수까지.
  - 응답 → 다음 요청: 가짜 SES가 응답을 보낸 때부터 다음 알림 요청이 도착한 때까지. 앱이 결과를 기록하고 다음 묶음을 준비하는 시간이다.

- 모든 시나리오에서 묶음 상태의 `ACCEPTED` 수와 가짜 SES가 접수한 수신 주소 수가 같다. 조용한 유실과 모르는 주소의 접수는 0이다.
- `response-loss`의 중복 101건 중 한 주소는 2번 중복됐다. 늦은 응답으로 실패한 묶음의 재시도가 다시 100번째 요청에 걸렸다.
- `response-loss`는 늦은 응답마다 발송이 10초(응답 제한) 멈췄다. 첫 실행이 `normal`보다 992초 길었다(늦은 응답 100번 × 10초). 실패한 100건은 그 실행이 끝난 뒤 재시도로 접수돼 총 소요가 더 늘었다.

- 종료 신호를 받은 이전 앱은 30초 동안 계속 보냈다. Spring의 종료 대기(30초)가 끝나도 발송 스레드는 멈추지 않았다. 스케줄러가 실행 중인 채로 JPA와 커넥션 풀이 닫히고 JVM이 끝나, 그때 보내던 묶음이 접수된 채 `PENDING`으로 남았다. 배포마다 중복 1건이다. 이전 앱의 발송 요약 로그는 남지 않았다(로컬 리허설에서 본 그대로다).

- 배포 3번으로 `normal`보다 124초(회차당 약 41초) 더 걸렸다.

### 5.4 SES 장애(`outage-10m`, `outage-1h`)

| 시나리오 | 시도 횟수 분포 | 첫 접수까지 p50 / 최대 |
| --- | --- | --- |
| `outage-10m` | 1번 6,117, 2번 3,883 | 22.9분 / 35.9분 |
| `outage-1h` | 2번 382, 3번 6,162, 4번 3,456 | 73.2분 / 92.0분 |

발송 실행별로 보면 아래와 같다. 발송 시작은 `outage-10m` 04:39:00, `outage-1h` 00:41:30이다.

| 시나리오 | 실행 | 끝난 시각(걸린 시간) | 보낸 묶음 | 접수 | 재시도 대기 |
| --- | --- | --- | --- | --- | --- |
| `outage-10m` | 1 | 05:04:44(25.7분) | 10,000 | 6,117 | 3,883 |
| `outage-10m` | 2 | 05:14:53(9.9분) | 3,883 | 3,883 | 0 |
| `outage-1h` | 1 | 01:07:28(26.0분) | 10,000 | 0 | 10,000 |
| `outage-1h` | 2 | 01:32:10(24.7분) | 9,618 | 0 | 9,618 |
| `outage-1h` | 3 | 01:53:36(21.1분) | 8,193 | 4,737 | 3,456 |
| `outage-1h` | 4 | 01:58:29(4.5분) | 1,807 | 1,807 | 0 |
| `outage-1h` | 5\~13 | 02:03:32 \~ 02:13:30(9번, 각 2분 이내) | 3,456 | 3,456 | 0 |

- **1시간 장애에서 기한 안에 접수된 묶음은 10,000, 최종 실패는 0이다.** 마지막 접수는 02:13으로 기한(11-12 00:00)보다 21시간 이상 앞이다.
- 500 응답에도 성공과 같은 지연을 줬으므로, 모두 실패하는 실행도 1만 통에 26분이 걸렸다.
- **재시도는 간격대로 나가지 않았다.** 한 실행은 시작할 때 재시도 시각이 된 묶음만 읽고, 그 뒤에 시각이 된 묶음은 다음 실행이 읽는다. `outage-1h` 첫 묶음의 1분 뒤 재시도는 26.0분 뒤(01:07:30)에, 5분 뒤 재시도는 다시 25.0분 뒤(01:32:30)에 나갔다.
- 앞 실행의 끝에서 실패한 묶음은 다음 실행이 시작할 때 아직 재시도 시각이 아니어서 한 실행을 건너뛴다. 2번째 실행이 382건, 3번째 실행이 1,807건을 건너뛰었다.
- `outage-1h`에서 장애가 끝난 01:41:30에 3번째 실행이 진행 중이었다.
  - 그 실행의 남은 4,737건과 4번째 실행의 1,807건은 장애가 끝나고 17분 안에(01:58:29까지) 접수됐다.
  - 장애가 끝나기 전 3번째 시도까지 실패한 3,456건은 30분 뒤 재시도를 기다려 02:03:00\~02:13:30에 접수됐다. 장애가 끝나고 21\~32분 뒤다.
- 재시도가 간격대로 나갔다면 첫 묶음은 0·1·6·36분의 네 번을 장애 안에서 모두 실패하고 2시간 뒤 재시도(2시간 36분)에 접수된다. 이번에는 실행이 길어 시도가 늦게 나가면서 장애 안에서 세 번만 실패했고, 92분에 끝났다.

**실측하지 않은 긴 장애(계산).** 08:00 묶기 직후 장애가 시작돼 끝나지 않는다고 가정하고 첫 묶음의 시도 시각을 셌다. 재시도 간격, 30초 cron, ID 순 처리, 실패 한 건에 155.8ms(`outage-1h` 첫 실행 1,558.4초 ÷ 1만 건)를 넣었다. 같은 계산으로 `outage-1h`를 세면 실행별 묶음 수(10,000 → 9,627 → 8,075 → 1,925)와 마지막 접수(91.0분)가 실측과 거의 같다.

| 시도 | 간격대로라면 | 실행 시간을 넣으면 |
| --- | --- | --- |
| 1 | 08:00 | 08:00 |
| 2(1분 뒤) | 08:01 | 08:26(첫 실행이 끝난 뒤) |
| 3(5분 뒤) | 08:06 | 08:51(두 번째 실행이 끝난 뒤) |
| 4(30분 뒤) | 08:36 | 09:21 |
| 5(2시간 뒤) | 10:36 | 11:22 |
| 6(6시간 뒤) | 16:36 | 17:22 |

- 6번째 시도는 첫 묶음이 17:22, 마지막 묶음이 17:51이다. 장애가 약 9시간 20분을 넘으면 최종 실패가 생기기 시작하고, 약 9시간 50분을 넘으면 1만 통이 모두 최종 실패한다. 24:00 기한보다 6번째 시도가 먼저 끝난다.
- 실제 SES 장애의 오류 응답이 더 빠르면 실행이 짧아져 표의 왼쪽 열에 가까워진다.

### 5.6 발송 처리량과 다른 예약 작업

`normal`의 1만 통은 한 번의 발송 실행(1,541.2초)으로 나갔다.

| 항목 | 값 |
| --- | --- |
| 요청 간격 | 평균 154.1ms(p50 112.0ms) |
| 그중 SES 응답(가짜 SES 지연) | 평균 135.6ms(p50 92.8ms) |
| SES 응답 뒤 다음 요청까지(앱의 기록·다음 묶음 준비) | 평균 18.6ms(p90 21.1ms) |
| 100ms 간격 제한(`awaitTurn`)에 걸린 요청 | 약 1%(SES 응답이 80ms보다 빨랐던 97건). 더 기다린 시간은 합쳐 0.6초 |
| app VM CPU / db VM CPU(평균) | 1.5% / 10.4% |
| 커넥션 풀 활성(평균) | 0.07 |

- **발송 속도는 한 건씩 차례로 보내는 구조와 SES 응답 시간이 정한다.** 요청 한 건에 SES 응답 약 136ms와 앱 처리 약 19ms가 차례로 든다. 자원은 거의 쓰지 않는다. 100ms 간격 제한은 거의 걸리지 않았다.
- 결정 0048은 "초당 10건이면 1,000통에 약 100초"로 잡았다. 실측은 초당 6.49건, 1,000통에 약 154초다. 앱 처리 시간을 0으로 줄여도 SES 응답이 평균 136ms라 초당 7.4건이 상한이다.
- **다른 예약 작업이 밀린 시간**
  - 수집·묶기·인증 기록 파기를 꺼 두었으므로, 이 측정에서 같은 스레드를 쓰는 작업은 `LoginAttemptLimiter.evictExpired`(15분 `fixedDelay`)뿐이다.
  - 지표 `tasks_scheduled_execution_seconds`로 보면 `evictExpired`는 발송 실행이 끝난 직후에만 실행됐다. 실행 시각은 01:07, 01:32, 01:53, 02:09, 02:41, 05:05, 05:43, 06:12이다. `kill`·`deploy`로 앱을 다시 시작한 02:45\~04:30 구간은 뺐다.
  - 15분 간격인 작업의 실행 사이가 가장 길 때 38분(05:05 → 05:43)이었다.
  - 발송 실행이 스레드를 붙잡은 최대 시간은 `normal` 25.7분, `outage-1h` 26.0분, `response-loss` 42.2분이다.
  - 그 동안 15분마다 돌아야 할 작업이 한 번도 돌지 못했다. 같은 스레드를 쓰는 수집(04:00), 묶기(08:00), 인증 기록 파기(04:30)도 발송 중이면 같은 시간만큼 밀린다.
- **10만 통 환산**(1만 통 실측 × 10)

  | 항목 | 값 |
  | --- | --- |
  | 소요 시간 | 15,411초, 약 4시간 17분 |
  | 스케줄러 스레드를 붙잡는 시간 | 같음. 한 번의 실행이 다 보낸다 |
  | SES 하루 할당량 | 24시간에 5만 통. **10만 통은 할당량의 2배다** |
  | SES 초당 한도 | 14통. 발송 속도(초당 6.49통)는 그 46%다 |

  - 할당량을 넘으면 그 뒤 요청은 SES가 거절한다. 그 오류를 앱이 일시 실패로 보는지 재시도 불가로 보는지는 확인하지 않았다.
  - 같은 날 계정 메일도 이 할당량을 나눠 쓴다.
  - 10만 통에서는 SES 장애가 있으면 실패하는 실행도 4시간 넘게 걸린다. 그날 기한까지 시도는 3\~4번에 그친다(5.4절과 같은 계산).
  - 규모 가정(하루 1만 통)은 할당량의 20%다.

## 6. 정합성과 한계

### 실제 SES로 나간 요청이 없었다는 근거

- 측정용 실행 구성은 SES 주소를 가짜 SES로 돌리고 가짜 접근 키를 넣는다. 설정이 잘못돼 실제 SES에 닿아도 인증에서 거절된다.
- `run.sh`는 시나리오마다 시작 전에 앱 컨테이너의 환경 변수에 가짜 SES 주소와 수집 끄기가 있는지 확인했다. `switch.sh on`은 합성 묶음 1건을 가짜 SES가 접수하는지 보고 시작했다.
- 모든 시나리오에서 묶음의 `ACCEPTED` 수가 가짜 SES의 접수 주소 수와 같다(조용한 유실 0). 실제 SES로 나간 묶음이 있으면 앱은 `ACCEPTED`로 기록하지만 가짜 SES 기록에는 없어 조용한 유실로 잡힌다.
- 계정 메일도 k6 요청 2,881건과 가짜 SES가 받은 계정 메일 2,881건이 같다.
- 측정이 끝난 뒤 CloudWatch(서울 리전) `AWS/SES`의 `Send`에서 2026-11-11 00:30\~06:20 KST를 봤다. 실제로 나간 메일은 0통이었다.
- 2026-11-10 첫 측정 뒤에도 같은 지표에서 2026-11-10 00:50\~10:35 KST를 봤다. 실제로 나간 메일은 00:58 사전 측정 100통뿐이었다.

### 정리 결과

- 시나리오마다 끝난 뒤 합성 사용자·묶음·가짜 새 혜택·계정 메일 인증 기록이 모두 0건이었다(`cleanup.txt`).
- 측정이 끝난 뒤 `switch.sh off`가 기본 실행 구성으로 app을 다시 만들었다. `app.env`·`compose.yaml` 해시와 `APP_TAG`가 측정 전과 같았고, Tunnel을 다시 켰다(`finish.txt`, `run.log`).

### 2026-11-10 첫 측정과 다시 잰 이유

2026-11-10 01:46\~08:00에 같은 8개 시나리오를 한 번 쟀다(커밋 `0294b6c`). 그 측정과 결과 검토에서 측정 도구의 결함을 찾아 고치고 전부 다시 쟀다. 첫 측정의 원본 결과는 저장소에 두지 않고, 아래 값만 남긴다.

- **가짜 SES가 응답마다 약 41ms를 더했다.** 응답의 헤더와 본문을 따로 쓰면서 Nagle 알고리즘을 켜 두었다. 본문이 클라이언트의 지연 ACK(리눅스 약 40ms)를 기다렸다 나갔고, 가짜 SES는 그 전에 응답 시각을 적었다. 그래서 늦어진 시간이 "응답 → 다음 요청"에 들어가 앱 처리 시간처럼 보였다. 응답을 한 번에 곧바로 보내게 고쳤다(`f05e1e7`). 로컬 컨테이너에서 재현하면 고치기 전 왕복 43.0ms, 고친 뒤 1.3ms였다.
- **`kill`이 1회차만 돌았다.** 회차 계획을 `while read`로 읽는데, 루프 안의 `ssh`가 표준 입력에서 남은 계획을 읽어 버렸다. 로컬 리허설은 `ssh` 대신 `bash -c`를 써서 드러나지 않았다. `ssh -n`과 별도 파일 설명자로 고친 뒤(`c894858`) 그날 09:51\~10:31에 `kill`만 다시 쟀다.
- **재개 시각을 잘못 찾았다.** 처음에는 UP 뒤에 온 요청만 재개로 봤다. 그래서 UP을 보기 직전에 다시 시작한 `kill` 5·10회차의 재개를 놓치고 다음 회차의 끊김을 잡았다. 이전 앱이 끝난 뒤 온 요청을 재개로 보도록 고쳤다(`d5d4f61`).
- `meta.json`의 `DEPLOY_AT_MIN`이 공백에서 나뉘어 잘못 기록됐다. 실제 배포 시각은 맞았고, 기록 형식만 고쳤다(`5e75a08`).

| 항목 | 첫 측정(2026-11-10) | 이 보고서(2026-11-11) |
| --- | --- | --- |
| 못 받은 묶음, 끝나지 않은 묶음, 최종 실패 | 모든 시나리오 0 | 모든 시나리오 0 |
| 중복 접수(`kill` / `deploy` / `response-loss`) | 10 / 3 / 101 | 10 / 3 / 101 |
| `kill` 다시 UP까지 / 재개까지 평균(최대) | 8.9\~9.5초 / 23.3초(36.0초) | 9.0\~9.4초 / 23.4초(36.0초) |
| `deploy` 이전 앱의 마지막 요청 / 재개까지 | 30.4\~30.7초 / 59.5초 | 30.6\~30.7초 / 59.4\~59.6초 |
| 끈 뒤 나간 알림(`notify-off`) | 0 | 0 |
| 응답 → 다음 요청(`normal` 평균) | 59.2ms | 18.6ms |
| `normal` 총 소요 / 초당 접수 | 1,947.5초 / 5.13 | 1,541.1초 / 6.49 |
| `outage-1h` 총 소요 / 시도 횟수 분포 | 5,580.0초 / 2번 1,665, 3번 8,335 | 5,520.0초 / 2번 382, 3번 6,162, 4번 3,456 |
| 실패한 계정 메일(`account-mail`) | 8건 | 79건 |

- 유실·중복·재개 시간은 두 측정이 같다. 도구가 더한 시간과 상관없는 값이다.
- 시간과 처리량은 달라졌다. 첫 측정은 요청마다 약 41ms가 더 들어 발송 속도가 21% 낮았다.
- `outage-1h`는 총 소요가 비슷하지만 경로가 다르다. 첫 측정은 한 실행이 33분이라 장애 안에서 두 번만 실패했다. 이번에는 한 실행이 26분이라 3,456건이 세 번 실패해 30분 대기에 걸렸다.
- 실패한 계정 메일이 늘어난 것은 알림이 빨라져 몰린 구간의 합계가 초당 약 15건에서 16.2건으로 올랐기 때문이다. 첫 측정에서는 버킷이 구간이 끝나기 직전에야 비었다.

### 한계

- 측정하는 동안 수집·묶기·인증 기록 파기를 껐으므로, 이 작업들과 발송이 스레드를 다투는 경우는 재지 않았다. 밀릴 수 있는 상한은 발송 한 실행의 길이다(5.6절).
- 가짜 새 혜택 3건으로 고정했다. 묶음에 든 혜택 수가 달라지면 메일 준비 시간(요청 사이 약 19ms)이 달라진다.
- SES 응답 지연은 app VM에서 잰 100건의 표본이다. 시간대와 날에 따라 실제 지연은 다를 수 있고, 발송 속도와 계정 메일 실패 수는 이 지연에 따라 달라진다(첫 측정과의 차이가 그 예다).
- SES 장애는 즉시 오는 500 응답으로만 주입했다. 응답이 아예 오지 않는 장애(연결·응답 시간 초과)는 재지 않았다(2026-11-09 결정). 이때는 한 건마다 최대 10초를 기다리므로 실행이 훨씬 길어진다.
- 2시간·6시간 뒤 재시도와 최종 실패는 실측하지 않고 계산했다(5.4절).
- 시나리오마다 한 번 쟀다. 강제 종료 시각은 시드로 고정했다.
- 여러 작업자의 동시 점유와 대상 선정·묶기 시간은 범위 밖이다(#138).

## 7. 확인된 문제(후속 이슈 후보)

| 문제 | 근거 | 사용자에게 생기는 일 |
| --- | --- | --- |
| 배포 때 발송이 종료 대기 동안 멈추지 않고 보내던 도중에 끝난다 | 5.3절. 배포마다 중복 1건, 이전 앱이 30초 더 보냄, 발송 요약 없음 | 배포마다 한 명이 같은 알림을 두 번 받는다 |
| 발송 속도가 결정 0048의 가정의 65%다 | 5.6절. 초당 6.49건. 한 건씩 보내 SES 응답(평균 136ms)을 매번 기다림, 자원 사용 낮음 | 1만 통에 25.7분, 10만 통에 4.3시간. 뒤쪽 사용자일수록 늦게 받는다 |
| 한 번의 발송 실행이 공용 스케줄러 스레드를 끝날 때까지 붙잡는다 | 5.4·5.6절. 1만 통에 26\~42분 동안 다른 예약 작업이 돌지 못함. 1분 뒤 재시도가 26분 뒤에 나감 | 수집·묶기가 발송 중이면 밀린다. 재시도 간격이 설계와 다르다 |
| 10만 통이면 SES 하루 할당량을 넘는다 | 5.6절. 할당량 5만 통 | 할당량을 넘긴 뒤의 알림과 그날 계정 메일이 나가지 않는다 |
| 계정 메일이 알림과 초당 한도를 나눠 쓰고 실패해도 다시 보내지 않는다 | 5.5절. 2분 몰림에 79건 실패 | 가입하려는 사람이 인증번호를 받지 못한다 |

SES 접수 뒤 기록 전 종료와 응답 유실에서 생기는 중복(5.1·5.2절)은 결정 0048이 받아들인 한계다. SES가 같은 요청을 한 번만 처리하게 하는 키를 받지 않기 때문이다. 이 측정은 그 빈도(종료·응답 유실 한 번에 1건)를 쟀다.

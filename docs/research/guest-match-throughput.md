# 비회원 조건 비교 목록의 처리량 개선 (#98)

비회원 조건 비교 목록(`POST /api/matches`)의 처리량 한계를 올린 작업을 [측정 기록 형식](../product/development.md#측정-기록-형식)에 맞춰 남긴다. 기준 측정은 [부하 테스트 기준 측정](load-test-baseline.md)(#96)이다. 설계와 단계는 [플랜](../plans/98-guest-match-throughput.md), 판정 입력을 두는 방식은 [결정 0038](../decisions/0038-match-list-snapshot.md)에 있다.

- 원본 결과
  - 로컬: `guest-match-throughput/local/`. 버전마다 `before/`(개선 전), `columns/`(대안 A), `snapshot/`(채택안)에 다음 파일을 둔다.
    - `rate-<속도>.json`: k6 요약
    - `rate-<속도>-breakdown.md`: CPU·할당 분해
    - `cpu.tsv`: 프로세스 CPU 시간
  - 로컬 공통: `explain-analyze.txt`(실행 계획), `columns/experiment.patch`(대안 A의 실험 변경)
  - 운영: `guest-match-throughput/results/`. 형식은 기준 측정과 같다.
- 재현: 로컬은 `scripts/loadtest/local-profile.sh`, 운영은 `scripts/loadtest/run.sh`다.

## 1. 사용자에게 생기는 문제와 재현 조건

- **문제**: 조건 비교 목록은 초당 7\~8건에서 한계였다(#96). 넘으면 p95가 2.4초로 늘었다. 판정하는 동안 DB 커넥션을 쥐어, 혼합 시나리오에서는 검색·상세까지 느려졌다. 혼합 16건에서 28건으로 올렸을 때 검색 p95는 72ms에서 257ms, 상세 p95는 29ms에서 190ms가 됐다.
- **재현 조건**
  - 운영: #96과 같은 스크립트·판정 기준·입력(`INPUTS`)으로 `guest-match`와 `mixed`를 잰다(5절).
  - 원인 확인과 대안 비교: 로컬에서 같은 요청으로 요청 1건의 비용을 나눠 잰다(4절, 5절).

## 3. 요청 분포와 실행 방식

### 운영

#96과 같다([기준 측정 3절](load-test-baseline.md#3-요청-분포와-실행-방식)). 자동 단계는 시작 속도부터 두 배씩 올리므로, 기준 측정의 단계(조건 비교 1·2·4·8, 혼합 2·4·8·16·32)를 앞부분에 포함한다.

### 로컬

- 요청: k6 v2.3.0의 `guest-match.js`를 #96 `inputs.json`(프로필 200개, 시드 96)으로 보냈다. 쪽은 1\~3, 지역 범위는 기본값이다. 실행기는 `constant-arrival-rate`다.
- 순서: 버전마다 앱을 새로 띄우고, 초당 1건으로 1분 워밍업한 뒤 속도마다 2분씩 쟀다.
- 구간마다 남긴 것: JFR(`profile` 설정), 구간 앞뒤 스레드 덤프, 앱 프로세스 CPU 시간. `local-breakdown.py`로 나눠 본다.
  - 스레드 묶음별 CPU: 스레드 덤프의 `cpu=` 증가량. 요청 처리, GC, JIT를 나눈다.
  - 요청 처리 CPU의 단계별 몫: JFR CPU 샘플의 스택으로 정한다.
  - 할당: 요청 스레드의 누적 할당량(`jdk.ThreadAllocationStatistics`) 증가량이다. JFR 할당 샘플은 초당 개수가 제한돼 요청 사이에 쌓인 양이 다음 요청의 첫 할당에 몰려 잡힌다. 그래서 할당은 단계별로 나누지 않는다.
- JIT 차이: (가)는 스크립트 확인용 짧은 실행(약 1분 30초)이 먼저 돌아 JIT가 더 데워져 있었다. 그래서 초당 1건 구간은 버전마다 JIT 몫이 달라, 버전 비교는 초당 4건 구간으로 한다.

## 4. 기준 구현의 결과와 원인 근거

### 운영(#96)에서 본 것

- 요청 1건에 app VM이 DB에서 약 25MB를 받았다. 요청 수에 정확히 비례했다(`prometheus.json`의 `vm_network_received`).

  | 단계(/s) | 1 | 2 | 4 | 8 |
  | --- | --- | --- | --- | --- |
  | app VM 수신(MB/s) | 25.1 | 50.2 | 100.4 | 199.0 |

- 초당 8건에서 app CPU 92%, db CPU 70%, 힙 최대 2,147MiB, GC 정지 24%, 풀 활성 평균 8.9였다.

### 요청 1건이 읽는 데이터(로컬 실데이터)

| 대상 | 크기 |
| --- | --- |
| benefit 전체 컬럼(개선 전 `findAll`) | 12.05MB |
| 그중 TEXT 4개(`target`·`selection_criteria`·`support_content`·`phone_inquiry`) | 7.35MB |
| benefit 중 목록 항목과 판정에 필요한 컬럼 | 2.51MB |
| benefit 중 판정 컬럼(`service_id`·`user_type`·`agency_type`·`agency_code`) | 0.40MB |
| 지원조건 원문(`source_record`, `SUPPORT_CONDITIONS`) | 8.74MB |

- 운영의 25MB는 benefit 전체와 지원조건 원문(약 20.8MB)에 프로토콜 비용이 더해진 값으로 본다.
- 실행 계획(`explain-analyze.txt`)
  - benefit 전체 컬럼은 전체 스캔 뒤 정렬에 42ms가 걸렸다. 필요한 컬럼만이면 8ms다.
  - `source_record`는 `endpoint` 인덱스가 없어 3만 2,850행을 모두 읽고 1만 950행을 걸렀다(15.7ms).

### 요청 1건의 CPU(로컬, 개선 전)

| 구간 | p50 / p95(ms) | 전체 CPU(ms) | 요청 처리 | GC | JIT | 할당(MB) | GC 정지(ms) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 초당 1건 | 264 / 278 | 241 | 149 | 81 | 8 | 335.1 | 11.6 |
| 초당 4건 | 202 / 218 | 151 | 117 | 30 | 3 | 336.5 | 5.7 |

CPU와 GC 정지는 요청 1건당 값이다.

요청 처리 CPU의 단계별 몫(초당 4건, JFR CPU 샘플 1,668개):

| 단계 | 비율 | 요청 1건당(ms) |
| --- | --- | --- |
| 지원조건 원문 파싱(Jackson) | 64.5% | 76 |
| Hibernate(엔티티 적재·영속성 컨텍스트) | 12.5% | 15 |
| JDBC 드라이버(결과 읽기·문자열 디코딩) | 9.8% | 12 |
| 판정(`ConditionMatcher` 등) | 6.8% | 8 |
| 운영 기관 지역 찾기(`Regions`) | 1.9% | 2 |
| DB 연결 TLS | 0.8% | 1 |
| 그 밖 | 3.7% | 3 |

### 원인

- 요청마다 지원조건 원문 1만 950건을 JSON으로 파싱한다. 이것이 요청 처리 CPU의 3분의 2다.
- 요청 1건이 약 335MB를 할당한다. 그래서 GC가 전체 CPU의 20\~34%를 쓴다. 운영에서 초당 8건에 힙이 상한 가까이 오르고 GC 정지가 24%였던 것과 맞는다.
- 혜택 엔티티 적재와 JDBC 읽기가 그다음이다(합쳐 약 22%). 판정 자체는 요청 1건에 6\~8ms였다.
- 이 모든 일을 클래스 단위 readOnly 트랜잭션 안에서 해서, 요청 내내 커넥션을 쥔다. Spring 7.0.9 `HibernateJpaDialect`는 readOnly 트랜잭션을 시작할 때 커넥션을 먼저 잡는다.

## 6. 정합성과 한계

### 결과가 같다는 근거

- 판정 입력을 만드는 쿼리 3개와 파싱은 개선 전 코드를 그대로 옮겼다. 판정은 같은 `ConditionMatcher.match`이고, 순서는 DB가 정렬한 순서를 그대로 쓴다.
- 기존 조건 비교 테스트를 고치지 않고 통과했다. `MatchListApiTest`는 로그인 목록의 판정·순서·건수·범위·쪽을, `PublicMatchApiTest`는 비회원 목록이 같은 프로필의 로그인 목록과 같은지를 본다.
- 로컬 실데이터에서 응답 표본 42개를 (가)·(나)·(다)로 받아 비교했다. 표본은 프로필 20개와 빈 프로필을 기본·전체 범위로 각각 받고, 첫 쪽 100건씩이다. 건수, 판정, 항목별 이유, 순서가 바이트 단위로 같았다.

### 허용 지연과 어긋나는 구간

- 목록은 마지막으로 끝난 수집 기준이다. 수집이 도는 동안부터 교체가 끝날 때까지는 직전 수집 기준이다(`DEC-FRESHNESS`). 로컬 전체 수집은 37.6초였다.
- 그 사이 DB를 바로 읽는 상세 비교·검색·상세와 목록이 다를 수 있다.
- 교체에 실패하면 비우고, 다음 요청이 DB에서 다시 만든다.

### 캐시 정확성 요구사항(`REQ-QUALITY-02`)

- 사용자별 데이터: 스냅샷에는 혜택 쪽 값만 있다.
- 비어 있을 때: 첫 요청 하나가 만들고 나머지는 기다린다(`MatchCandidateStoreTest`).
- 늦게 끝난 생성: 수집 전에 시작한 생성이 교체보다 늦게 끝나도 교체한 것이 남는다. 가짜 loader를 래치로 멈춰 재현했다(`MatchCandidateStoreTest`). 교체가 잠금을 쓰지 않게 바꾸면 이 테스트가 실패하는 것을 확인했다.

### 측정의 한계

- 로컬은 앱·DB·부하 도구가 같은 기기라 절대값을 운영과 비교하지 않는다. JFR(`profile`)의 오버헤드도 버전마다 같게 들어 있다.
- 단계별 몫은 JFR CPU 샘플 비율로 나눈 추정이다. 비교에 쓴 구간(초당 4건·32건)의 샘플은 358\~1,714개다. (다)의 초당 1건은 요청 처리가 가벼워 75개뿐이라 단계별 몫을 쓰지 않는다.
- 앱은 한 대라는 전제다(결정 0038). 앱을 늘리면 인스턴스마다 교체 신호가 필요하다.
- 혜택 수가 늘면 판정 비용도 비례해 늘어난다. 지금은 1만 950건에 요청 1건당 판정 6\~13ms다.

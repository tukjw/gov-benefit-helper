# 부하 테스트 기준 측정 (#96)

운영 API의 기준 지연·처리량·오류율과 한계 지점을 [측정 기록 형식](../product/development.md#측정-기록-형식)에 맞춰 남긴다. 측정 방식은 [결정 0037](../decisions/0037-proxmox-deploy-metrics-and-load-test.md), 재현 스크립트는 `scripts/loadtest/`, 원본 결과는 `docs/research/load-test-baseline/results/`에 있다. 병목의 개선과 성능 목표 결정은 다루지 않는다.

## 1. 측정 대상과 재현 조건

- 시나리오: 혜택 검색, 혜택 상세, 비회원 조건 비교 목록, 로그인, 혼합(검색 40%·상세 35%·조건 비교 20%·로그인 5%, 가정 비율)
- 측정 일시: 2026-10-31(토) 19:36~22:08(KST). 측정하는 동안 API를 막았다. 04:00 예약 수집 시간대(03:30~05:00)와 겹치지 않는다.
- 실행: 부하 생성 VM에서 `scripts/loadtest/run.sh all`(커밋 `e5888f1`). 절차는 [부하 테스트](../ops/load-test.md)다.
- 사용자에게 생기는 문제: 한계를 넘는 요청이 오면 응답이 수 초에서 30초까지 늦어진다. 로그인은 그 일부가 500 오류로 끝난다(4절).
- 원본 결과: 시나리오마다 `results/<시각>-<시나리오>/`에 다음 파일을 둔다.
  - `meta.json`: 실행 정보, 단계별 시작·끝 시각, 한계 판정
  - `<단계>.json`: k6 요약
  - `vmstat-<단계>.txt`: 부하 생성 VM의 CPU
  - `prometheus/<단계>/`: 서버 지표
  - `inputs.json`: 준비 데이터
  - `app-log-check.txt`: 앱 로그에서 `수집`·`메일`을 찾은 결과
- 다시 잴 때: `inputs.json`을 `INPUTS`로 넘기면 같은 입력으로 잰다.

## 2. 데이터와 실행 환경

- 데이터
  - 혜택 10,942건(실데이터, 출처 공공서비스 API)
  - 테스트 계정 1,000개(합성, 측정 뒤 삭제)
  - 준비 데이터: 서비스 ID 1,000개, 조건 비교 프로필 200개(시드 96)
- 앱
  - 이미지 `v0.1.1`
  - 실행 구성은 이 브랜치의 `deploy/app/compose.yaml`을 손으로 반영했다. app VM의 파일 해시가 저장소와 같다(`9247526b…`).
  - 측정 직전 앱 컨테이너를 다시 만들었다. 앱 안의 캐시는 없다.
- 호스트: Proxmox 한 대(Ryzen 7 8845HS, RAM 32GB). CPU 클럭은 `amd-pstate` 드라이버의 `schedutil` governor라서 사용량에 따라 오르내린다.
- VM 사양: 모두 같은 호스트에 있고 내부 브리지로 연결된다.

  | VM | vCPU | 메모리 |
  | --- | --- | --- |
  | app | 4 | 3,909MiB |
  | db | 2 | 3,910MiB |
  | 부하 생성 | 2 | 3,910MiB |

- 설정
  - 커넥션 풀 10, Tomcat 최대 스레드 200. 둘 다 기본값이다.
  - JVM 힙 상한 2,304MiB(컨테이너 메모리 3GB × `MaxRAMPercentage=75`)
  - MySQL 8.4, 버퍼 풀 1GB. 측정 중 InnoDB 디스크 읽기는 초당 5회 이하여서 데이터가 버퍼 풀 안에 있었다.
- 부하 도구
  - k6 `grafana/k6:2.3.0`, 실행기는 `constant-arrival-rate`다.
  - 가상 사용자는 `max(20, 요청 속도)`개를 미리 만들고, 최대 1,000개까지 쓴다.

## 3. 요청 분포와 실행 방식

- 단계마다 3분, 시나리오마다 첫 단계 앞에 워밍업 3분을 둔다. 워밍업은 기준값에서 뺀다.
- 단계는 `run.sh`가 정한다.
  - 시작 속도에서 두 배씩 올려 한계 단계를 찾는다. 시작 속도는 검색·상세·로그인이 초당 5건, 조건 비교 1건, 혼합 2건이고, 상한은 1,280건이다.
  - 한계가 나오면 마지막 정상 속도로 3분 회복한 뒤 그 사이를 25% 간격으로 다시 잰다.
- 한계 판정(결정 0037): 다음 중 하나가 처음 나온 단계를 한계로 본다.
  - 응답 수가 목표의 95% 미만이다.
  - 못 보낸 요청(`dropped_iterations`)이 1건 이상이다.
  - 오류율이 1%를 넘는다.
  - p95가 첫 단계 p95의 2배를 넘고, 늘어난 폭이 50ms 이상이다.
- 요청
  - 가상 사용자마다 `CF-Connecting-IP`를 다르게 붙인다. 응답 본문은 버린다(`discardResponseBodies`).
  - 측정 중에는 API를 막았다(`cloudflared` 중지). 앱에 닿은 요청은 부하 도구가 보낸 것뿐이다.
- 표의 값
  - 지연은 k6 `http_req_duration`으로, 실패한 요청도 포함한다. 단위는 ms다.
  - 처리량은 응답 수 ÷ 180초다. 과부하 단계는 단계가 끝난 뒤 받은 응답도 포함한다.
  - 서버 지표는 Prometheus 값(15초 간격, `[1m]` 창)이다. 단계 시작 1분 뒤부터 끝까지의 평균을 적었다. 첫 1분에는 앞 단계 값이 섞이기 때문이다.
  - 풀 활성·대기는 HikariCP의 활성 연결 수와 연결을 기다리는 스레드 수다.
  - 부하 VM 유휴는 `vmstat`의 유휴 CPU 최솟값이다.

## 6. 정합성과 한계

### Cloudflare를 거치지 않았고 실제 요청이 섞이지 않았다는 근거

- **측정 내내 `cloudflared`가 멈춰 있었다.** `run.sh`가 시나리오를 시작할 때마다 확인했다.
- **앱의 요청 카운터가 k6가 보낸 수와 정확히 같다.** 측정 직전 앱을 다시 만들어 카운터가 0에서 시작했다.
  - `/api/matches`: 조건 비교 시나리오가 끝난 뒤 6,846이다. k6가 보낸 수도 6,846건이다.
  - `/api/auth/login`: 로그인 시나리오가 끝난 뒤 66,288이다. k6가 보낸 수도 66,288건이다.
  - `/api/benefits`: 로그인 시나리오 동안 128,928이다. 검색 시나리오에서 k6가 보낸 128,884건에, 그때까지 네 시나리오의 준비 단계(`prepare.py`)가 보낸 11건씩을 더한 값과 같다.
  - 로그인 시나리오 동안 다른 경로의 카운터는 늘지 않았다.
- **429는 한 건도 없었다.** 조건 비교를 초당 8건(10초에 80회)으로 보낸 단계도 같았다. 200이 아닌 응답은 로그인 과부하 단계의 500뿐이다.

### 메일 발송과 공공 API 호출이 없었다는 근거

- **앱 지표:** 다섯 시나리오의 측정 구간 모두에서 수집 실행(`collection_runs_total`)과 메일 경로의 요청 수 지표가 없었다. 앱을 다시 만든 뒤 한 번도 생기지 않았다는 뜻이다.
- **앱 로그:** 측정 구간에서 `수집`·`메일`을 찾은 결과(`app-log-check.txt`)가 다섯 시나리오 모두 비어 있다.
- **Resend:** 대시보드에 측정 시간대의 발송 기록이 없다(측정 뒤 확인).

### 테스트 계정 정리와 측정 뒤 상태

- **테스트 계정:** `accounts.sh cleanup` 뒤 테스트 계정이 0개, 그 계정의 리프레시 토큰이 0개였다. 비밀번호 파일도 지웠다.
- **앱 상태:** API를 풀기 전에 `UP`이었고, 로그에 `OutOfMemoryError`가 없었다. API를 푼 뒤 외부 주소의 응답이 200이었다.
- **LAN 차단:** LAN의 다른 기기에서 app VM의 LAN 주소 8080에 닿지 않았다.

### 측정의 한계

- **부하 생성 VM은 병목이 아니었다.** 유휴 CPU가 모든 단계에서 62% 이상이었다. 기준은 20%다.
- **한 번만 측정했다.**
  - 같은 측정 안에서 같은 속도를 다시 잰 단계는 거의 같은 값이 나왔다. 회복 단계의 p95는 처음 잰 단계와 5% 안팎으로 같았다(검색 80건 34 → 35ms, 로그인 40건 78 → 74ms, 조건 비교 4건 577 → 585ms).
  - 날을 달리해 다시 쟀을 때 얼마나 흔들리는지는 모른다. 그래서 한계는 범위로 읽는다(4절).
- **호스트 CPU 클럭이 사용량에 따라 오르내린다(`schedutil`).**
  - **낮은 부하에서 오히려 느렸다.** 부하가 오를수록 p50이 줄었다. 상세는 10ms에서 2.5ms로, 로그인은 136ms에서 63ms로, 검색은 57ms에서 20ms로 줄었다.
  - **p95 기준값이 높게 잡혔다.** 기준이 가장 느린 첫 단계의 p95이기 때문이다. 검색 120건이 정상으로 판정된 이유다.
  - **CPU 사용률을 요청 수에 비례해 읽으면 안 된다.** 클럭이 오르면 CPU 사용률은 덜 오른다.
  - **한계 근처 값은 높은 클럭에서 쟀다.** 이때는 CPU가 차 있기 때문이다.
  - 다음 측정과 비교할 때는 governor가 같은지 먼저 확인한다.
- **부하 VM과 지표 VM의 시계가 어긋나 보인다.**
  - 단계 시작 시각의 지표에 이미 그 단계의 요청이 들어 있었다. 부하 VM 시계가 15초 안팎 앞선 것으로 보인다.
  - 서버 지표는 단계 시작 1분 뒤부터 평균했다. 구간을 15초 당겨 다시 계산해도 CPU·풀 값이 1%p 안쪽으로 같았다.
- **지표 창(`[1m]`)에 앞 단계가 섞인다.** 로그인 회복 단계와 혼합 워밍업의 지표에 로그인 500이 보인다. 이는 앞 단계의 꼬리다. k6가 받은 응답에는 오류가 없었다.
- **상세 조회는 한계를 찾지 못했다.** 상한(초당 1,280건)에서 멈췄다.
- **혼합의 비율은 가정이다.** 실사용 비율이 아니다. 28건의 판정 근거도 약하다(4절).
- **재지 않은 것:** 로그인한 사용자의 개인 API, 메일 경로, Cloudflare를 거친 구간이다(플랜의 범위 밖).

### 확인된 병목(개선은 별도 이슈)

- **검색:** db VM CPU가 초당 120~140건에서 찬다.
- **비회원 조건 비교 목록:** 초당 7~8건에서 app CPU가 차고, 힙 사용량이 상한에 가까워진다. 판정하는 동안 커넥션을 쥔다. 혜택이 늘면 한계가 더 낮아질 것으로 본다(추정).
- **로그인:** BCrypt로 app CPU가 차면, 트랜잭션이 커넥션을 쥔 채 CPU를 기다린다. 그래서 풀이 막히고 30초 뒤 500이 난다.

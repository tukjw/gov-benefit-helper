# 구현 플랜

이슈 하나당 플랜 파일을 최대 하나 둡니다. 파일명은 이슈 브랜치와 같은 `<이슈번호>-<슬러그>.md`입니다.

## 플랜을 두지 않는 경우

- 이슈의 완료 조건만으로 구현 방법이 하나로 정해지는 변경은 플랜을 생략할 수 있습니다. 예: 지침·스킬 문구 수정, 오타, 설정값 하나 변경, 의존성 버전 올리기.
- 대안 중 하나를 골라야 하거나, 여러 레이어에 걸치거나, `결정 필요` 항목이 생길 수 있는 변경은 플랜을 둡니다.
- 릴리스 PR은 대응하는 이슈가 없으므로 플랜을 두지 않습니다.
- 이슈 PR에서 플랜을 생략하면 PR 설명에 `플랜: 없음`을 적습니다.
- 플랜 없이 작업하다가 설계 판단이 필요해지면 진행을 멈추고 플랜을 작성합니다.

## 헤더

첫 줄의 `status` 아래에 제목과 브랜치를 적습니다. 이슈는 제목의 `#<이슈번호>`로 가리키고 URL은 적지 않습니다. 브랜치 줄에는 분기 원점과 그 시점의 커밋을 함께 남깁니다.

```
status: draft

# 구현 계획 — #<이슈번호> <이슈 제목>

브랜치: `<브랜치 이름>` (develop `<sha>` 기준)
```

hotfix 플랜만 `main` 기준으로 적습니다.

## 상태

파일 첫 줄에 `status: draft | in-progress | done`을 둡니다.

- `draft`: 작성됨. 아직 착수하지 않음.
- `in-progress`: 브랜치에서 작업 중.
- `done`: PR을 올림. PR 직전 마지막 커밋에서 바꾸며, 머지 후에도 기록으로 남깁니다.

## 작성 시점

선행 이슈가 머지된 뒤에 작성합니다. 선행 결과에 따라 시그니처나 파일 위치가 바뀌므로 미리 써 두면 낡습니다.

## 필수 항목

- 목표 및 범위 (포함, 제외)
- 확인된 사실과 제약
- 설계 결정 (대안이 있을 때만, 결정 문서로 올린 결정은 링크)
- 단계별 구현 계획 (파일과 함수 이름 명시)
- 완료 조건 매핑 (이슈의 완료 조건을 그대로 복사)
- 검증 명령
- 결정 필요 (없으면 "없음")

## 설계 결정과 결정 문서

플랜은 해당 이슈의 기록이라 이슈가 끝나면 고치지 않습니다. 그래서 이슈가 끝난 뒤에도 지켜야 하는 결정은 [`docs/decisions/`](../decisions/README.md)에 결정 문서로 올립니다.

- 결정을 내린 이슈가 끝난 뒤에도 다른 이슈의 코드·스키마·설정이 따라야 하면 결정 문서로 올립니다. 플랜의 `설계 결정`에는 결정 요지와 결정 문서 링크를 적습니다.
- 그 이슈의 구성 방법에 그치는 결정은 플랜에만 남깁니다.
- `AGENTS.md`에 규칙으로 있는 결정은 결정 문서로 올리지 않습니다.
- 제품 동작에 관한 결정은 `docs/product/development.md`의 `DEC-*`로 둡니다.
- 플랜을 쓸 때 [결정 목록](../decisions/README.md#결정-목록)에서 `채택` 상태인 결정을 확인하고 따릅니다. 따를 수 없으면 새 결정 문서로 대체하는 작업을 플랜에 포함합니다.

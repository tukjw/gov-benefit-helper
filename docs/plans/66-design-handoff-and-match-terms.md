## 설계 결정

2026-10-26 사용자 결정. 대안은 같은 날 대화에서 비교했다.

1. **보관 구조: 채택 범위 문서를 입구로 두고 원본 사본은 하위 폴더에 둔다.**
   - `docs/design/README.md`: 채택 범위 문서. `docs/README.md`에서 이 문서로 연결한다.
   - `docs/design/handoff/`: 원본 사본(`README.md`, `prototype/gov-benefit-helper.dc.html`, `prototype/support.js`). 내용은 고치지 않는다. 시안이 바뀌면 사본을 통째로 교체하고 채택 범위 문서를 고친다.
   - 대안: 채택 범위를 원본 README에 덧붙임. 원본과 우리 판단이 섞여 시안을 교체할 때 판단이 사라진다.
2. **예시 데이터: 프로토타입 HTML 안의 예시는 원본대로 두고 `data/benefits.sample.json`만 넣지 않는다.**
   - 이슈 작업 내용의 "금액·기간이 가짜인 예시 혜택 데이터는 넣지 않는다"를 바꾼 것이다. HTML의 `const B`를 지우거나 바꾸면 완료 조건 "프로토타입을 열면 시안 화면이 보인다"를 지킬 수 없거나 화면 모양이 시안과 달라진다.
   - 별도 JSON은 화면 확인에 필요 없고, 떼어진 데이터 파일은 테스트·개발 데이터로 가져다 쓰기 쉬워 넣지 않는다.
   - `docs/design/README.md` 맨 위에 "정책 이름은 실제지만 금액·신청 기간은 시안용 예시이며 사실이 아니다. 구현·테스트 데이터로 쓰지 않는다"와 JSON을 보관하지 않았다는 점을 적는다.
   - 대안: 금액·기간을 '예시' 문구로 바꿈(원본이 아니게 되고 글자 길이가 달라짐), 예시를 모두 지움(목록·상세가 빈 화면이 됨).
3. **화면 문구에 내부 용어를 쓰지 않는다. 요구사항에는 의미를, 채택 범위 문서에는 문구 예시를 둔다.**
   - `REQ-MATCH-01`에 적는 원칙: '해당'에는 공개 데이터의 대상 조건과 입력한 정보를 비교한 결과이며 실제 지원 여부는 기관 심사로 정해진다는 안내를 함께 표시한다. 화면 문구에는 '지원조건 코드' 같은 내부 용어를 쓰지 않는다. 이슈 완료 조건의 "지원조건 코드 기준임과 기관 심사 안내"를 사용자 문장으로 옮긴 것이다.
   - 화면이 안내를 고르는 근거는 응답의 `notices`(`CODE_BASED`, `NOT_FINAL` 등)다. 문구 예시는 `docs/design/README.md`의 F3에 둔다. 예: "공개된 대상 조건과 입력한 정보를 비교한 결과예요. 실제 지원 여부는 담당 기관 심사로 정해져요."
   - 대안: 요구사항에 화면 문구를 고정. 화면을 만들며 다듬을 때마다 요구사항을 고쳐야 한다.
4. **용어를 바꾸는 기준은 '판정 결과를 가리키는가'다.**
   - 결과 이름(‘부합’), 결과에 이르는 동사(‘부합한다’, ‘새로 부합하게 된’), 결과로서의 ‘불일치’를 바꾼다. 문장은 '해당한다', '새로 해당하게 된', '미해당'으로 자연스럽게 고친다.
   - 데이터 대조 결과('경로 간 불일치', '근사 5, 불일치 2')와 비밀번호 불일치는 그대로 둔다.
   - 결정 0022는 고치지 않는다(확인된 사실). 결정 문서는 기술 결정의 기록이고 화면 용어의 기준은 `REQ-MATCH-01`이다.
   - 코드 이름(`MATCH`, `MISMATCH`, `CODE_INCLUDES` 등)은 바꾸지 않는다(이슈 완료 조건).
5. **화면 용어와 판정 코드의 대응은 `REQ-MATCH-01`과 `MatchResult` 주석에 둔다.**
   - `MATCH` = 해당, `NEEDS_CHECK` = 확인 필요, `MISMATCH` = 미해당. 프론트가 코드를 표시 용어로 바꿀 때 한 곳을 보면 된다.
   - `MatchResult` 주석은 각 값의 뜻 앞에 표시 용어를 적는 데 그친다. OpenAPI 설명은 바꾸지 않는다.
6. **채택 범위 문서의 구성**
   - 머리말: 시안 출처와 받은 날짜, 보관 위치, 예시 데이터 경고(설계 2), 프로토타입 여는 법(인터넷 필요, 첫 화면이 간편인증이라 상단 메뉴로 이동).
   - 채택: 디자인 토큰(색, 타이포그래피, 간격, 모서리, 컨트롤 높이, 그림자), 공통 레이아웃(페이지 컨테이너, 헤더·모바일 헤더, 푸터, 브레드크럼, 토스트), 공통 컴포넌트(혜택 카드, 칩 버튼, 라디오 카드, 단계 표시, 입력·에러 표시, 빈 상태, 사이드 박스), 글자 크기 조절, 접근성 기준(시안의 KWCAG 체크와 본문 바로가기 추가). KRDS 공식 컴포넌트 도입 여부는 F1에서 정한다.
   - 공식 정부 사이트 요소 제거와 민간 서비스 안내:
     - 쓰지 않음: 공식 배너와 태극기, 정부 상징 로고, "공식 전자정부 누리집" 문구, '웹 접근성 품질인증' 링크(받지 않은 인증).
     - 대신: 배너 자리(같은 회색 띠)에 "정부 공식 누리집이 아닌 개인이 운영하는 민간 서비스입니다. 혜택 정보는 행정안전부 공공서비스(혜택) 정보를 바탕으로 하며, 신청은 각 기관에서 합니다." 로고는 서비스 이름 글자 로고. 푸터에 데이터 출처(공공데이터포털, 이용 조건)와 운영자 연락처.

# 개발 순서·결정할 사항

작성일: 2026-09-27. 아래 순서는 제안이며 GitHub 이슈가 생성된 상태는 아니다. 실제 이슈 번호·파일·함수는 선행 작업이 끝난 뒤 [구현 플랜 규칙](../plans/README.md)에 맞춰 작성한다.

## 권장 개발 순서

| 순서 | 작업 단위 후보 | 관련 요구사항 | 완료 증거·선행 조건 |
| --- | --- | --- | --- |
| 0 | 공공 API 인증 호출·데이터 품질 확인 | REQ-DATA-02, REQ-MATCH-01 | 완료. [데이터 검증 보고서](../research/gov24-api-data.md)(#5)와 이를 근거로 한 DEC-SCOPE/DATA/PROFILE/MATCH [결정](#결정한-사항) |
| 1 | 정책 저장 모델·첫 수집·실행 이력 | REQ-DATA-01, REQ-DATA-02, REQ-QUALITY-01 | 마이그레이션, 반복/부분 실패 수집 검증, 저장 데이터 조회. 0 선행 |
| 2 | 정책 검색·상세 API | REQ-SEARCH-01, REQ-DETAIL-01 | 필터·정렬·페이지·누락 정보·외부 장애 중 조회 검증. 1 선행. DEC-SEARCH, DEC-AUTH의 공개 범위, DEC-FRESHNESS의 정보 표시 기준은 정했다 |
| 3 | 사용자 식별·최소 프로필 | REQ-ACCOUNT-01, REQ-PROFILE-01 | 사용자 간 접근 차단·이메일 소유 확인·토큰 만료와 재사용 감지·탈퇴 삭제·프로필 변경·미입력 검증. DEC-AUTH, DEC-PROFILE, DEC-APP은 정했다 |
| 4 | 관심 정책·검증된 조건 비교 | REQ-SAVE-01, REQ-MATCH-01 | 동시 저장·사용자 분리·조건 경계값·확인 필요 사례. 2·3 및 DEC-MATCH 선행 |
| 5 | 알림 기본 흐름과 복구 검증 | REQ-NOTIFY-01, REQ-NOTIFY-02 | 설정→예약→발송, 취소/변경/재시도/재시작 후 복구 검증. 4 및 DEC-NOTIFY 선행 |
| 6 | 조건에 맞는 새 혜택 알림 | REQ-NOTIFY-03, REQ-NOTIFY-02 | 새 혜택 감지→대상 선정→발송, 최초 수집·재수집·규칙 변경 시 잘못된 알림이 없는지 검증. 4 및 DEC-NOTIFY/MATCH 선행 |
| 7 | 관심 혜택 변경 알림 | REQ-NOTIFY-04, REQ-NOTIFY-02 | 변경 감지→발송, 수집 시각·규칙 변경·수집 실패를 변경으로 알리지 않는지 검증. 4 및 DEC-NOTIFY 선행 |

5~7번의 순서는 `DEC-NOTIFY`에서 정한다. 먼저 만드는 쪽이 `REQ-NOTIFY-02`의 발송·복구 기반을 함께 만든다.

표의 완료 증거는 [요구사항](requirements.md)의 P0 조건 기준이다. 각 요구사항의 P1 조건은 해당 기능의 P0 조건을 완성한 뒤 별도 이슈로 다룬다. 1차·2차의 P1은 0~4번으로 개인화 MVP를 완성한 다음 착수한다.

성능·캐시 개선은 순서에 미리 두지 않는다. 측정으로 문제가 확인되면 이슈로 만들고 [측정 기록 형식](#측정-기록-형식)에 맞춰 남긴다.

작업 단위는 이슈 후보이며 반드시 한 행이 한 이슈일 필요는 없다. 특히 알림은 설정·예약, 발송 작업자, 장애 복구를 나눌 수 있다.

0번 데이터 검증은 끝났고 `DEC-DATA`가 정해져 1번을 착수할 수 있다. 알림(5~7번)은 `DEC-SCOPE`에 따라 첫 공개(2차 MVP) 이후에 한다.

### 운영 작업

기능 순서와 별개로 진행한다. 배포할 기능이 생기기 전에 인프라를 먼저 키우지 않는다. O1은 기능과 독립적이라 0번과 함께 진행할 수 있다.

| 순서 | 작업 단위 후보 | 관련 요구사항 | 시점·완료 증거 |
| --- | --- | --- | --- |
| O1 | PR 자동 테스트와 머지 보호 | REQ-OPS-01 | 지금 착수 가능. PR에서 Testcontainers를 포함한 테스트가 실행되고, 실패하면 머지가 막히는지 확인 |
| O2 | 컨테이너 이미지·인프라 코드·운영 배포 | REQ-OPS-01 | 2번 이후. 릴리스 태그로 운영 배포, 직전 릴리스로 되돌리기 검증. DEC-OPS 선행 |
| O3 | 기본 지표·경보·백업 | REQ-OPS-02 | O2와 함께 또는 직후. 연속 수집 실패 경보, 정기 백업 생성 확인 |
| O4 | 무중단 배포·배포 중 작업 보존·복구 연습 | REQ-OPS-01, REQ-OPS-02 | P1. 4번 이후, 알림 작업자는 5~7번 이후. 배포 중 오류율, 작업 유실 여부, 복구 시간 측정 |

## 이슈에 넣을 내용

이슈에는 사용자에게 달라지는 결과, 관련 요구사항 ID, 이번 범위, 그대로 검증할 완료 조건, 선행 작업을 적는다. 구현 플랜에는 실제 코드 기준 파일·함수·설계 대안·테스트 명령을 적는다.

예시 — ‘관심 정책 저장·해제’ 이슈 후보:

- 목표: 로그인한 사용자가 혜택을 저장하고 해제할 수 있다.
- 요구사항: `REQ-SAVE-01` 중 저장·해제·중복 방지·사용자 분리.
- 완료 조건: 동시 저장 후 한 건, 반복 해제 후 미저장, 타 사용자 기록 변경 불가, 존재하지 않는 혜택 저장 거절.
- 제외: 알림 예약과 관심 목록 검색. 별도 이슈에서 연결한다.
- 검증: 인증 경계 검증, Testcontainers MySQL의 실제 유니크 제약·동시 요청 검증.

제품 문서의 미정 사항은 해당 기능에 착수하기 전에 해결한다. 이슈 플랜에 `결정 필요`가 남아 있다면 임의로 확정하지 않고 저장소 지침을 따른다.

## 알려진 위험

- 외부 API의 호출 한도·응답 지연·실패와 명세에 없는 필드 의미. 수집은 시간 제한·재시도 상한·호출 예산 안에서 실행한다(`REQ-QUALITY-01`).
- 수집과 조회가 같은 DB를 쓴다. 수집 중 조회 지연 여부는 수집 실행과 조회 경로의 지표를 구분해 관찰한다.
- 알림은 외부 제공자를 거친다. 발송 중 종료나 응답 유실 시 유실·중복이 생길 수 있으므로 발송 의도를 DB에 영속한다(`REQ-NOTIFY-02`). 별도 outbox·메시지 브로커는 필요할 때 도입한다.
- 배포는 실행 중인 수집·알림 작업을 중단시킨다. 중단된 작업은 재시작 후 이어서 처리할 수 있어야 한다.
- 데이터 규모는 0번 전까지 모른다. 검색 성능과 캐시 필요성은 실제 규모와 측정으로 판단한다.

위험이 실제 문제로 관찰되면 이슈로 만들고 아래 형식으로 기록한다.

## 측정 기록 형식

개선 이슈에서는 다음을 함께 남긴다.

1. 사용자에게 생기는 문제와 재현 조건.
2. 데이터 규모·출처, 실행 환경·서버 수·설정, 코드 커밋.
3. 요청 분포·동시성·지속 시간·워밍업·캐시 상태.
4. 기준 구현의 지연·처리량·오류율·DB 지표와 원인 근거.
5. 비교한 대안, 선택 이유, 같은 조건의 개선 후 결과.
6. 기능·정합성이 유지되는지와 실패·복구 상황의 한계.

실데이터와 합성 확장 데이터, 실제 사용량과 부하 도구의 요청을 구분한다. 실패 요청을 제외한 지연만으로 성능을 좋게 보이게 하지 않는다. 재현 스크립트와 원본 결과는 해당 성능 작업에서 경로를 정해 추가한다.

| DEC-NOTIFY | 채널·예약 시점·시간대·변경/취소 경계·유효기한·동의 단위, 기한·새 혜택·변경 알림의 순서, 새 혜택 알림의 대상 기준, 변경 알림 대상 항목 | 첫 채널 하나. 세 알림의 순서는 데이터 검증에서 확인한 기한·조건 품질로 정함. 새 혜택 알림은 ‘부합’만 대상으로 하는 안을 검토. 변경 알림은 신청기한·지원 대상·신청 방법부터 검토. 같은 날짜 재수집은 재알림 사유가 아님 | 알림 설계 전 |

| DEC-OPS | 배포 대상·서버 수·환경 수·인프라 코드 도구·컨테이너 실행 방식·관측 도구·백업 방식·성능 목표·메일 발송 서비스·프론트 배포 위치 | 현재 Spring Boot/MySQL로 기준 구현. 서버 한 대의 컨테이너 배포부터 시작하고, API·수집·알림 작업자의 실행 방식이 달라지면 오케스트레이션을 검토. 첫 구현을 위해 모든 항목을 한 번에 결정할 필요는 없다. 실제 데이터로 확인 가능한 문제부터 해소하고 해당 기능의 결정만 확정한다.

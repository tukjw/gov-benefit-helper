# 외부 데이터와 검증 계획

작성일: 2026-09-27. 공개 안내와 명세를 바탕으로 작성했고, 2026-09-28 실제 호출로 확인한 사실을 [데이터 검증 보고서](../research/gov24-api-data.md)에서 옮겨 반영했다. 아래의 정규화·저장 방식은 우리 서비스의 설계 제안이다.

## 사용할 API

[행정안전부 대한민국 공공서비스(혜택) 정보](https://www.data.go.kr/data/15113968/openapi.do)를 주 데이터 출처로 삼는다. 포털은 무료·개발/운영 자동승인, 이용허락범위 제한 없음, 개발계정 트래픽 10,000을 안내한다. 실제 계정의 한도 단위·호출 제한은 활용신청 화면과 응답으로 확인한다. 포털 페이지의 수정일은 개별 혜택의 최신성이나 갱신 주기가 아니다.

기본 주소: `https://api.odcloud.kr/api/gov24/v3`

| GET 경로 | 용도 |
| --- | --- |
| `/serviceList` | 목록·요약·기관·분야·출처 수정일 수집 |
| `/serviceDetail` | 상세 조건·방법·기한·서류·신청처 수집 |
| `/supportConditions` | 구조화된 연령·소득구간·생활 상태 등의 조건 확인 |

세 응답은 `서비스ID`로 연결한다. 공통 페이지 인자는 `page`, `perPage`이며 기본값은 각각 1, 10이다. 인증은 `serviceKey` 쿼리 또는 `Authorization: Infuser <키>` 헤더로 한다. 상세·조건도 페이지 조회로 전체를 받을 수 있으므로 혜택마다 별도 호출하지 않는다. [공식 API 명세](https://infuser.odcloud.kr/api/stages/44436/api-docs?1684891964110)

실제 호출로 확인한 사실(2026-09-28, 근거는 [데이터 검증 보고서](../research/gov24-api-data.md)):

- 세 경로 모두 10,941건이고 서비스ID 누락·중복·경로 간 불일치가 없었다. 1,000건씩 33회 호출(29초, 원문 43MB)로 전체를 받는다.
- `perPage`를 크게 해 응답이 약 4MB를 넘으면 200 `{"code":0,"msg":"정상"}`만 오고 `data`가 빠진다. `data`가 없는 200은 실패로 다룬다.
- 지원조건 코드 값은 `"Y"` 또는 `null`(연령은 정수)이다. `Y`는 그 속성이 있는 사람도 대상이라는 뜻이다. 그룹 전부 `Y`와 '해당사항없음' 단독 `Y`는 제한이 없다는 뜻으로 읽힌다. 대상을 좁힌 표본 66건 중 12건은 원문과 맞지 않았으므로, 코드만으로 불일치를 확정하지 않는다.
- 신청기한은 상시 60.3%, 미확인 27.8%, 명시 날짜 5.7%, 조건부 3.9%, 신청 불필요 2.2%다. 명시 날짜의 24%는 지난 연도만 적혀 있다.
- 대상 지역 필드는 없다. 지자체 소관 혜택은 소관기관명에 시도가 있지만, 거주 요건이 원문에 적힌 것은 시군구 혜택의 51.5%다. 기관명이 거주 요건을 뜻하지 않는다.
- 목록 수정일시·등록일시는 `yyyyMMddHHmmss`, 상세 수정일시는 `yyyy-MM-dd`이며 시간대 표기가 없다. 수정일시 필터는 목록에만 있다.

남은 미확인:

- 한 사람이 같은 그룹의 여러 속성을 가졌을 때의 조합 방식, 그룹 사이의 관계, 사업자 대상 코드 13개의 의미.
- 데이터 갱신 주기, 수정일시와 실제 내용 변경의 관계, 목록에서 사라진 항목의 의미. #6에서 여러 시점을 비교해 보고서에 추가한다.
- 세 경로의 공통 스냅샷·버전 보장, 페이지 크기 한계의 정확한 값, 호출 제한 초과·시간 초과 응답의 형식.

확인한 사실도 제공기관이 보장한 것은 아니다. 실제 응답에서 관찰한 범위를 넘어 우리 서비스의 보장으로 만들지 않는다. [공식 API 명세](https://infuser.odcloud.kr/api/stages/44436/api-docs?1684891964110)

## 우리 서비스의 데이터 책임

아래는 개념 구분이며 테이블을 각각 만들라는 지시는 아니다. 실제 응답을 확인한 뒤 ERD와 저장 단위를 정한다.

| 데이터 | 보존할 내용 | 사용 원칙 |
| --- | --- | --- |
| 수집 원문 | 출처·경로·서비스 ID·수집 시각·원문 또는 재검증 가능한 스냅샷 | 인증 헤더/키 제외. 보관 기간·변경분 보관 방식은 수집량 확인 후 결정 |
| 조회용 혜택 | 이름·요약·기관·분야·안내/신청 링크·원문 참조 | 공통 검색·상세의 기준 |
| 정규화 정보 | 해석 가능한 날짜·조건, 해석 상태·규칙 버전 | 모르는 정보를 NULL 한 가지로 뭉개지 않고 이유를 구분 |
| 수집 실행 | 실행 ID·범위·상태·실패 구간·건수 | 완료·부분 실패·실패와 재처리 이력을 확인 |
| 사용자 정보 | 계정·최소 프로필·관심 목록·알림 설정 | 공공 원문·공통 캐시와 구분 |
| 알림 의도 | 대상·기한/설정 버전·예약 시각·처리 상태·시도 이력 | 도입 단계에서 논리적 중복 기준과 보관 기준 결정 |

상세나 조건 하나가 실패했다고 다른 경로의 성공 데이터를 버리지 않는다. 반대로 세 경로가 서로 다른 시점에 수집됐는데 같은 시점의 완전한 자료인 것처럼 취급하지 않는다. 사용자 조회에는 저장된 정보를 제공하되, 조건 비교·알림은 필요한 근거가 확보된 데이터만 사용한다.

## 데이터 검증 결과

인증 호출과 데이터 품질 확인 결과는 [공공서비스(혜택) API 실제 데이터 검증 보고서](../research/gov24-api-data.md)에 있다. 호출·집계 스크립트는 `scripts/research/gov24/`에 있다. 원문 스냅샷은 저장소 밖에 둔다. 테스트에 쓸 공개 fixture는 수집 구현 이슈에서 스냅샷에서 골라 백엔드 테스트 리소스에 둔다.

## 수집 구현에서 지킬 경계

- 시간 제한·제한된 동시성·재시도 예산을 먼저 둔다. 병렬 호출 수와 페이지 크기는 측정으로 정한다.
- 식별자를 기준으로 반복 처리에 안전하게 저장한다. 동일 내용은 불필요한 도메인 변경이나 알림을 만들지 않는다.
- 원문 수집 시간의 변경과 혜택 내용의 변경을 구분한다. 정규화 규칙 변경으로 생긴 차이를 외부 공고 변경처럼 알리지 않는다.
- 실패한 범위를 성공 체크포인트 뒤로 넘기지 않는다. 증분 수집은 수정일 경계 중복·지연 반영·삭제 누락을 함께 다룬다.
- 페이지 조회 중 원천 데이터가 바뀔 수 있다. 중복 제거는 누락 방지와 다르며, 우리 DB 트랜잭션만으로 원천 API의 스냅샷을 만들 수 없다.
- 전체 조회를 마쳐도 원천 스냅샷 보장이 생기지 않는다. 필요하면 반복 대조·재확인 방식을 정하고, 일시 미노출을 즉시 종료/삭제로 바꾸지 않는다.
- 실제 신청·수급 결과는 이 데이터 수집 범위가 아니다. 사용자가 직접 적는 준비 상태를 추가하더라도 정부의 처리 상태와 구분한다.

관련 요구사항: `REQ-DATA-01`, `REQ-DATA-02`, `REQ-MATCH-01`, `REQ-NOTIFY-01`, `REQ-QUALITY-01`.

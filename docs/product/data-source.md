# 외부 데이터와 검증 계획

작성일: 2026-09-27. 공개 안내와 명세를 확인했으며, 이 문서 작업에서는 인증키를 사용한 실제 호출을 수행하지 않았다. 아래의 정규화·저장 방식은 우리 서비스의 설계 제안이다.

## 사용할 API

[행정안전부 대한민국 공공서비스(혜택) 정보](https://www.data.go.kr/data/15113968/openapi.do)를 주 데이터 출처로 삼는다. 포털은 무료·개발/운영 자동승인, 개발계정 트래픽 10,000을 안내한다. 실제 계정의 한도 단위·호출 제한은 활용신청 화면과 응답으로 확인한다. 포털 페이지의 수정일은 개별 혜택의 최신성이나 갱신 주기가 아니다.

기본 주소: `https://api.odcloud.kr/api/gov24/v3`

| GET 경로 | 용도 |
| --- | --- |
| `/serviceList` | 목록·요약·기관·분야·출처 수정일 수집 |
| `/serviceDetail` | 상세 조건·방법·기한·서류·신청처 수집 |
| `/supportConditions` | 구조화된 연령·소득구간·생활 상태 등의 조건 확인 |

세 응답은 `서비스ID`로 연결한다. 공통 페이지 인자는 `page`, `perPage`이며 기본값은 각각 1, 10이다. 인증은 `serviceKey` 쿼리 또는 `Authorization` 헤더를 정의한다. 상세·조건에도 페이지 조회와 서비스 ID 필터가 있으므로 혜택마다 별도 호출해야 한다고 가정하지 않는다. [공식 API 명세](https://infuser.odcloud.kr/api/stages/44436/api-docs?1684891964110)

명세만으로 확정할 수 없는 부분:

- 지원조건 코드의 값 해석과 빈 값의 의미. 임의로 `Y/N`, 빈 값=제한 없음으로 변환하지 않는다.
- 신청기한·선정기준 문자열의 모든 형태와 실제 날짜 의미.
- 지역 판별. 구조화된 지원조건에 대상 지역 필드는 없으며 기관명이 거주 요건을 뜻하지 않는다.
- `perPage`의 최대값, 날짜 형식·시간대, 데이터 갱신 주기.
- 세 경로의 공통 스냅샷·버전 보장과 목록에서 사라진 항목의 삭제 의미.

위 한계는 공개 스키마에 해당 필드나 보장이 명시돼 있지 않다는 뜻이다. 실제 응답과 제공기관 설명을 확인하기 전에는 우리 서비스의 보장으로 만들지 않는다. [공식 API 명세](https://infuser.odcloud.kr/api/stages/44436/api-docs?1684891964110)

## 우리 서비스의 데이터 책임

아래는 개념 구분이며 테이블을 각각 만들라는 지시는 아니다. 실제 응답을 확인한 뒤 ERD와 저장 단위를 정한다.

| 데이터 | 보존할 내용 | 사용 원칙 |
| --- | --- | --- |
| 수집 원문 | 출처·경로·서비스 ID·수집 시각·원문 또는 재검증 가능한 스냅샷 | 인증 헤더/키 제외. 보관 기간·변경분 보관 방식은 수집량 확인 후 결정 |
| 조회용 혜택 | 이름·요약·기관·분야·안내/신청 링크·원문 참조 | 공통 검색·상세의 기준 |
| 정규화 정보 | 해석 가능한 날짜·조건, 해석 상태·규칙 버전 | 모르는 정보를 NULL 한 가지로 뭉개지 않고 이유를 구분 |
| 수집 실행 | 실행 ID·범위·상태·실패 구간·건수 | 완료·부분 실패·실패와 재처리 이력을 확인 |
| 사용자 정보 | 계정·최소 프로필·관심 목록·알림 설정 | 공공 원문·공통 캐시와 구분 |
| 알림 의도 | 대상·기한/설정 버전·예약 시각·처리 상태·시도 이력 | 도입 단계에서 논리적 중복 기준과 보관 기준 결정 |

상세나 조건 하나가 실패했다고 다른 경로의 성공 데이터를 버리지 않는다. 반대로 세 경로가 서로 다른 시점에 수집됐는데 같은 시점의 완전한 자료인 것처럼 취급하지 않는다. 사용자 조회에는 저장된 정보를 제공하되, 조건 비교·알림은 필요한 근거가 확보된 데이터만 사용한다.

## 첫 개발 작업 — 인증 호출과 데이터 검증

인증키는 로컬 환경 변수 등 저장소 밖의 설정으로 주입한다. 호출 결과를 문서나 fixture로 남길 때 요청 URL의 키와 인증 헤더를 제거한다.

| 확인할 항목 | 남길 결과 | 결정에 미치는 영향 |
| --- | --- | --- |
| 인증·페이지 조회 | 성공한 요청 형식, 응답 크기, 전체 건수, 적용 가능한 페이지 크기 | 초기 수집 시간과 호출 예산 |
| 세 경로 연결 | ID별 누락·중복·상세/조건 불일치 예시 | 부분 수집 상태와 저장 키 |
| 필드 품질 | 필수값 누락, 긴 텍스트, 링크, 날짜 형식, 결측 비율 | 컬럼·DTO·검증 규칙 |
| 조건 코드 | 실제 값 종류, 값의 의미를 확인한 근거, 공고와의 대조 사례 | 자동 비교할 항목과 보류할 항목 |
| 기한·지역 표현 | 명시 날짜·상시·조건부·미확인 예시, 대상 지역의 근거 | 지역 필터·접수 상태·알림 가능 범위 |
| 갱신·삭제 | 반복 수집 시 변경 사례, 수정일 필터 경계, 사라진 ID 처리 근거 | 전체/증분 수집과 정합성 확인 방식 |
| 실패 응답 | 인증 실패·제한·시간 초과의 구분과 제공되는 힌트 | 재시도·중단·관측 정책 |

표본은 특정 기관·분야만 보지 말고 여러 형태를 포함한다. 일부 표본으로 전체 데이터 의미가 검증됐다고 결론 내리지 않는다. 실제 호출 제한을 의도적으로 소진하는 실험은 하지 않고, 장애 재현은 로컬 stub으로 수행한다.

실측 보고서는 해당 이슈에서 `docs/research/`에 추가하고 확인 날짜·표본 수·집계 방법을 기록한다. 공개 가능한 fixture는 백엔드 테스트 리소스에 둔다. 인증 성공, 호출 한도, 해석 가능한 조건, 날짜 품질을 확인한 뒤 개인화 범위와 ERD를 확정한다.

## 수집 구현에서 지킬 경계

- 시간 제한·제한된 동시성·재시도 예산을 먼저 둔다. 병렬 호출 수와 페이지 크기는 측정으로 정한다.
- 식별자를 기준으로 반복 처리에 안전하게 저장한다. 동일 내용은 불필요한 도메인 변경이나 알림을 만들지 않는다.
- 원문 수집 시간의 변경과 혜택 내용의 변경을 구분한다. 정규화 규칙 변경으로 생긴 차이를 외부 공고 변경처럼 알리지 않는다.
- 실패한 범위를 성공 체크포인트 뒤로 넘기지 않는다. 증분 수집은 수정일 경계 중복·지연 반영·삭제 누락을 함께 다룬다.
- 페이지 조회 중 원천 데이터가 바뀔 수 있다. 중복 제거는 누락 방지와 다르며, 우리 DB 트랜잭션만으로 원천 API의 스냅샷을 만들 수 없다.
- 전체 조회를 마쳐도 원천 스냅샷 보장이 생기지 않는다. 필요하면 반복 대조·재확인 방식을 정하고, 일시 미노출을 즉시 종료/삭제로 바꾸지 않는다.
- 실제 신청·수급 결과는 이 데이터 수집 범위가 아니다. 사용자가 직접 적는 준비 상태를 추가하더라도 정부의 처리 상태와 구분한다.

관련 요구사항: `REQ-DATA-01`, `REQ-DATA-02`, `REQ-MATCH-01`, `REQ-NOTIFY-01`, `REQ-QUALITY-01`.

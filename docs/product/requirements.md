# 요구사항 초안

작성일: 2026-09-27. 아래는 개발 범위를 합의하기 위한 제안이며, 구현 완료 명세가 아니다. 제품 동작을 정리하고, 엔드포인트·테이블·클래스 설계는 이슈별 플랜에서 결정한다.

단계는 [서비스 기획](overview.md)의 1차 탐색, 2차 개인화 MVP, 3차 알림을 따른다. `DEC-*`는 [개발 순서와 결정 사항](development.md)의 결정 ID다.

## 우선순위

완료 조건에 P0·P1 우선순위를 붙인다.

- **P0**: 해당 기능이 끝까지 동작하는 데 필요한 조건. 사용자에게 틀린 정보를 보여주지 않는 것과 사용자 간 데이터 분리는 P0에 둔다.
- **P1**: 부분 실패 복구, 동시성, 장애 재현, 성능·캐시처럼 P0 기능을 완성한 뒤 문제를 재현하고 측정하며 다룰 조건. 측정 결과는 [측정 기록 형식](development.md#측정-기록-형식)에 맞춰 남긴다.

이슈는 P0 조건으로 먼저 만들고, P1 조건은 별도 이슈로 나눈다. P1 조건이 없는 동안에도 P0 조건만으로 틀린 결과를 만들지 않아야 한다. 예를 들어 실패 구간 재처리가 없더라도 전체 재실행은 안전해야 한다. P1 조건이 없는 요구사항은 P0만 적는다.

## 공통 용어와 표시 원칙

- **혜택**: 공공 API의 서비스 한 건. 내부 식별자 설계와 별개로 출처의 서비스 ID를 보존한다.
- **조건 비교**: 사용자가 입력한 정보와 검증된 일부 조건의 비교. 실제 수급 가능 여부의 확정이 아니다.
- **확인 필요**: 정보 누락·해석 미지원·조건 충돌 등으로 결론을 낼 수 없는 상태. ‘조건 불일치’와 구분한다.
- **관심 정책**: 사용자가 저장한 혜택. 저장만으로 알림 수신에 동의한 것으로 처리하지 않는다.
- **정보 갱신**: 출처의 수정 시각, 우리 서버가 수집한 시각, 정규화한 시각은 의미가 다르다.

## 1차 — 수집·검색·상세

### REQ-DATA-01 — 공공 데이터 수집

목적: 외부 API 호출 여부와 관계없이 우리 DB의 데이터로 탐색할 수 있다.

P0:

- 목록·상세·지원조건을 출처 서비스 ID로 연결하고, 필수 식별자가 없는 응답은 오류 기록과 함께 격리한다.
- 같은 응답을 반복 수집해도 혜택이 중복 생성되지 않는다.
- 수집 실행별 시작·종료 시각, 성공·부분 실패·실패 상태, 처리 건수를 확인할 수 있다.
- 일부 요청 실패 시 이전에 정상 저장한 데이터를 오류나 빈 값으로 덮어쓰지 않는다. 상세가 없는 신규 혜택은 정보 미수집 상태를 구분한다.
- 전체 재실행으로 다시 수집할 수 있고, 이때 중복 생성·정상 데이터 손상이 없다.
- 하루 1회 목록·상세·지원조건 전체를 수집한다.
- 수집 중 목록에서 보이지 않았다는 이유만으로 혜택을 삭제하거나 종료 처리하지 않는다. 혜택마다 목록에서 마지막으로 확인한 시각을 남긴다.
- 수집 실행 권한은 일반 사용자에게 공개하지 않는다.

P1:

- 실패 구간을 기록하고, 전체가 아닌 실패 구간만 다시 처리할 수 있다.
- 목록에서 사라진 혜택의 비노출·종료 판단 기준을 정하고 적용한다. 기준은 #6의 갱신·삭제 관찰 결과로 정한다.

실행 주기와 전체 수집 방식은 `DEC-DATA`에서 정했다. 증분 수집은 전체 수집의 비용이 문제로 관찰되면 다시 검토한다.

### REQ-DATA-02 — 원문·정규화·출처 구분

목적: 원문을 다시 확인하고 해석 오류를 바로잡을 수 있다.

P0:

- 해석에 사용한 원문을 보존하고, 정규화 결과에서 원문을 찾아갈 수 있다. 원문은 서비스별 최신 1벌과 내용이 바뀐 레코드의 이력을 보관하며, 조회수는 내용 변경 비교에서 뺀다(`DEC-DATA`).
- 출처 수정 시각이 없더라도 수집 시각으로 대신 표시하지 않는다. 사용자에게 수집 시각임을 구분한다.
- 신청기한은 최소한 명시 날짜·상시·예산 소진 등 조건부·미확인을 구분한다. 복수 모집 기간이나 애매한 문구는 원문과 확인 필요 상태로 남길 수 있다.
- 지역 정보가 없을 때 ‘전국’, 조건이 비어 있을 때 ‘누구나 신청 가능’으로 바꾸지 않는다.

P1:

- 변환 규칙의 버전 또는 변경 근거를 남긴다. 규칙 변경으로 생긴 차이를 출처 공고의 변경과 구분한다.
- 수동으로 검증한 정보에는 근거와 확인 시점을 남긴다. 새 원문과 충돌하면 검증된 정보처럼 계속 사용하지 않는다.

### REQ-SEARCH-01 — 혜택 목록과 검색

목적: 로그인하지 않고도 관심 있는 혜택을 찾을 수 있다. 비회원 공개는 `DEC-AUTH`에서 정했다.

P0:

- 기본 검색은 혜택 이름의 키워드, 분야·운영 기관 유형 필터를 제공한다. 키워드는 공백으로 나눈 단어를 모두 포함한 혜택을 찾고, 빈 키워드는 전체 목록으로 처리한다. 한 필터 안의 여러 값은 OR, 필터 사이는 AND로 적용한다.
- 정렬은 이름순, 동률은 서비스 ID 순이다. 변경되지 않은 데이터에서 페이지 이동 결과가 재현돼야 한다.
- 페이지당 기본 20건·최대 100건이다. 범위를 벗어난 페이지 번호·크기는 잘못된 입력으로 응답하고, 결과 없음과 마지막 쪽을 넘은 번호는 빈 목록으로 응답한다.
- 항목에 서비스 ID·이름·요약·기관명·기관 유형·분야·신청기한 원문 또는 표시 상태·목록에서 마지막으로 확인한 시각을 제공한다. 없는 값은 만들어 채우지 않는다.
- 목록에서 사라진 혜택은 비노출 기준(P1, #6)이 정해질 때까지 결과에 포함한다.
- 목록 요청은 공공 API를 직접 호출하지 않는다.

P1:

- 운영 기관 지역(소관기관 소재 시도·시군구) 필터를 추가한다. 이름은 ‘운영 기관 지역’으로 하고, 대상 지역·거주 요건처럼 표시하지 않는다(`DEC-SCOPE`). 소관기관으로 지역을 알 수 없는 혜택을 ‘전국’으로 채우지 않는다.
- 신청기한 정규화가 검증된 뒤 접수 중·마감 임박 필터를 추가한다.
- 한 번도 수집되지 않은 상태를 ‘검색 결과 0건’과 구분한다.

검색 계약은 `DEC-SEARCH`에서 정했다. 응답의 결과 건수는 규모가 커지면 뺄 수 있는 항목이며, 이를 만들었다는 이유만으로 전체 건수나 깊은 페이지 이동을 영구 요구사항으로 고정하지 않는다.

### REQ-DETAIL-01 — 혜택 상세와 신청처 안내

P0:

- 지원 내용·대상·선정기준·신청 방법·기한·서류·문의처·공식 출처를 제공한다. 누락된 항목은 ‘정보 없음’ 또는 ‘확인 필요’로 구분한다.
- 온라인 신청 URL과 안내 페이지 URL을 구분한다. 온라인 신청 URL이 없으면 접수 방법을 보여주며, 이 서비스에서 직접 신청이 끝난 것처럼 표시하지 않는다.
- 출처·수집 시점을 확인할 수 있다. 수집이 오래 중단돼도 저장된 상세를 조회할 수 있고, `DEC-FRESHNESS`의 기준(목록을 갱신한 마지막 수집 실행에서 48시간 경과)을 넘으면 오래된 정보임을 구분한다.
- 존재하지 않는 식별자는 찾을 수 없음으로 응답한다. 상세 미수집은 혜택 자체가 존재하지 않는 경우와 구분한다.
- 공통 상세 응답에 다른 사용자의 프로필·관심 저장·알림 설정이 섞이지 않는다.

## 2차 — 개인화 MVP

### REQ-ACCOUNT-01 — 사용자 식별과 내 정보 보호

선행 결정: `DEC-AUTH`. 로그인 제공자·세션/토큰 방식은 미정이다.

P0:

- 로그인 성공 시 같은 사용자를 지속적으로 식별하며, 인증되지 않은 개인 기능 요청은 거절한다.
- 다른 사용자 ID를 요청에 넣어도 그 사용자의 프로필·관심 목록·알림 설정을 읽거나 변경할 수 없다.
- 로그아웃과 세션 또는 토큰 만료 시의 동작을 인증 방식에 맞춰 정의하고 검증한다.
- 실제 사용자에게 공개하기 전 탈퇴 시 개인 데이터와 미발송 알림의 삭제·보관 기준을 결정하고 구현한다.

### REQ-PROFILE-01 — 최소 프로필 입력과 수정

선행 결정: `DEC-PROFILE`. 조건 비교(`REQ-MATCH-01`)와 운영 기관 지역 필터(`REQ-SEARCH-01`)에 쓰는 항목만 받는다.

P0:

- 받는 항목은 생년월일, 거주 시도·시군구, 성별, 가구·생애 속성(여러 개 선택, ‘해당 없음’ 포함)이며 모두 선택 입력이다. 소득은 받지 않는다.
- 나이는 생년월일로 만 나이를 계산한다.
- 거주 시도·시군구는 운영 기관 지역 필터의 기본값으로 쓰고, 조건 비교에서 거주 요건 판정에 쓰지 않는다.
- 프로필을 저장·조회·수정할 수 있고, 지원하지 않는 값이나 모순된 입력은 항목별 오류로 응답한다.
- 미입력과 ‘해당 없음’을 구분한다. 선택 항목을 비워도 검색·상세 조회를 사용할 수 있다.
- 프로필 변경 후 다음 조건 비교에는 바뀐 값이 적용된다.
- 주민등록번호·증빙서류 등 기능에 필요하지 않은 정보를 요구하지 않는다.

### REQ-MATCH-01 — 근거가 있는 조건 비교

선행 결정: `DEC-SCOPE`, `DEC-PROFILE`, `DEC-MATCH`. 비교 항목과 결과 기준은 `DEC-MATCH`를 따르고, 코드 의미의 근거는 [데이터 검증 보고서](../research/gov24-api-data.md#5-지원조건-코드)다.

P0:

- 비교 항목은 개인 대상 여부, 연령, 성별, 가구·생애 속성이다. 소득 등 그 밖의 조건은 비교하지 않은 조건으로 보여준다.
- 혜택마다 ‘부합’·‘확인 필요’·‘불일치’ 중 하나와 항목별 이유를 반환한다.
  - 부합: 비교 항목을 지원조건 코드상 모두 충족한다. 지원조건 코드 기준의 결과임을 표시한다.
  - 확인 필요: 코드상 벗어나거나, 해당 코드가 없거나, 연령이 코드의 경계값인 항목이 있다. 이유·원문·공식 링크를 함께 보여준다.
  - 불일치: 개인 대상이 아닌 혜택에만 쓴다. 개인 대상 혜택은 코드상 벗어나도 불일치로 처리하지 않는다.
- 일부 조건에 부합해도 혜택 전체를 ‘신청 가능 확정’으로 표현하지 않는다. 비교하지 못한 조건과 공식 확인 경로를 함께 제공한다.
- 같은 그룹 안의 코드는 OR, 그룹 사이는 AND로 해석한다. 검증된 관계가 아니라 해석 규칙임을 결과에 표시한다.
- 프로필 미입력이나 데이터 누락만으로 불일치 처리하지 않는다. 확인 필요 후보를 자동으로 완전히 숨기지 않는다.
- 결과는 부합 → 확인 필요 순으로 정렬하고, 같은 결과 안에서는 혜택 이름과 서비스 ID 순으로 정렬한다.
- 조건 경계값, 미입력, 서로 충돌하는 원문/정규화 사례로 결과와 근거를 검증한다.

남은 미확인:

- 그룹 안의 조합 방식과 그룹 사이의 관계는 확인하지 못했다. 위 해석 규칙을 쓰고, 공고 대조에서 반례가 나오면 규칙을 고친다.
- 연령 코드의 경계 포함 여부는 확인하지 못했다. 경계값은 확인 필요로 둔다.
- 개인 대상 여부의 판정 기준(목록의 사용자구분, 개인 대상 코드가 전부 null인지)은 조건 비교 구현 이슈에서 정한다.

이 요구사항의 분량은 조건을 처리하는 방식이 아니라 지원할 조건의 수로 조절한다. 의미가 검증된 조건 몇 개로 시작하고, 조건을 늘리는 작업은 별도 이슈로 나눈다.

### REQ-SAVE-01 — 관심 정책 저장·해제·목록

P0:

- 로그인한 사용자는 혜택을 저장·해제하고 자신의 관심 목록을 조회할 수 있다.
- 동시 저장이나 같은 요청의 재전송에도 사용자·혜택 조합은 한 건만 남는다. 이미 해제한 항목의 재해제도 결과 상태는 동일하다.
- 사용자 A의 저장·해제가 사용자 B의 목록에 영향을 주지 않는다.
- 관심 목록에서는 혜택의 현재 정보를 보여준다. 관심 기록을 임의로 삭제하지 않는다.
- 아직 존재하지 않는 혜택의 저장 요청을 거절한다. 출처 조회 실패를 혜택 종료로 간주하지 않는다.

P1:

- 출처에서 종료가 확인된 혜택은 관심 목록에 종료로 표시한다. 종료 판단은 `REQ-DATA-01` P1와 `DEC-DATA`를 따른다.

## 3차 — 알림

### REQ-NOTIFY-01 — 기한 알림 설정·변경·해제

선행 결정: `DEC-NOTIFY`. 채널·알림 시점·사용자 설정 단위가 정해져야 구현한다.

P0:

- 사용자가 명시적으로 알림을 설정한 관심 혜택만 발송 대상으로 삼는다.
- 날짜가 검증된 기한만 예약한다. 날짜만 있고 마감 시각이 없는 경우 임의의 정확한 마감 시각을 만들지 않는다.
- 알림 설정 변경 시 미발송 예약을 조정하고, 같은 논리적 알림이 중복 예약되지 않는다.
- 관심 해제 또는 알림 해제 시 아직 발송을 시작하지 않은 예약을 취소한다. 외부 전송이 시작된 알림의 회수를 보장하지 않는다.

P1:

- 재수집으로 기한이 바뀌면 미발송 예약을 조정한다.
- 기한 단축으로 이미 지나간 예약, 연장 후 재알림, 날짜 정보 소실의 처리 기준을 결정하고 검증한다.

### REQ-NOTIFY-02 — 발송 실패 복구와 상태 확인

P0:

- 예약 확정 후 프로세스가 종료돼도 미처리 발송 의도를 복구할 수 있다.
- 일시 실패는 정한 횟수·기한 안에서 재시도하고, 발송 성공과 최종 실패를 구분할 수 있다.
- 제공자 접수, 실제 전달, 사용자 읽음을 같은 상태로 기록하지 않는다. 채널이 제공하는 확인 범위만 노출한다.

P0는 발송 작업자 하나를 전제로 한다.

P1:

- 작업자를 여러 개 실행해도 동일 작업을 정상적으로 동시에 점유하지 않는다. 점유 만료 후 이전 작업자가 돌아오는 상황도 검증한다.
- 영구 실패·취소·만료·결과 불명 상태를 구분할 수 있다.
- 제공자 접수 성공 후 응답 유실을 테스트한다. 내부 중복 방지만으로 외부에서 정확히 한 번 전달된다고 주장하지 않는다.

### REQ-NOTIFY-03 — 조건에 맞는 새 혜택 알림

목적: 사용자가 모르던 혜택 중 자신의 조건에 맞는 것이 새로 수집되면 알 수 있다.

선행 결정: `DEC-NOTIFY`, `DEC-MATCH`. 어떤 조건 비교 결과를 알림 대상으로 볼지 정해져야 구현한다.

P0:

- 사용자가 새 혜택 알림에 따로 동의한 경우에만 보낸다. 관심 저장이나 기한 알림 설정을 이 알림의 동의로 보지 않는다.
- 새 혜택은 우리 DB에 처음 저장되는 출처 서비스 ID로 판단한다. 최초 전체 수집과 정규화 규칙 변경으로 생긴 차이는 새 혜택으로 알리지 않는다.
- 조건 정보가 아직 수집되지 않은 새 혜택은 건너뛰지 않고, 조건이 수집된 뒤 알림 대상을 판단한다.
- 알림 대상은 `DEC-NOTIFY`에서 정한 조건 비교 결과 기준을 만족하는 사용자로 한정한다. 비교 근거가 없는 혜택을 추측으로 알리지 않는다.
- 같은 사용자에게 같은 혜택을 두 번 알리지 않는다. 수집을 재실행해도 같다.
- 발송·재시도·복구는 `REQ-NOTIFY-02`를 따른다.

P1:

- 기존 혜택의 조건이 바뀌어 새로 부합하게 된 경우도 알린다. `REQ-DATA-02`의 변경 이력 보관과 규칙 버전 구분(P1)을 전제로 한다.
- 사용자 수가 많아도 대상 사용자 선정이 수집 작업을 지연시키지 않는다. 대상 선정 시간과 DB 부하를 측정한다.
- 여러 건을 묶어 보내고 사용자별 수신 빈도를 제한한다.

사용자가 프로필을 바꿔 새로 부합하게 된 기존 혜택은 이 알림의 대상이 아니다. 기존 혜택은 검색과 조건 비교로 찾는다.

### REQ-NOTIFY-04 — 관심 혜택 변경 알림

목적: 저장한 혜택의 기한·조건 등이 바뀌면 다시 찾아보지 않아도 알 수 있다.

선행 결정: `DEC-NOTIFY`. 어떤 항목의 변경을 알릴지와 동의 단위가 정해져야 구현한다.

P0:

- 사용자가 변경 알림에 동의한 관심 혜택만 대상으로 한다. 관심 저장만으로 동의한 것으로 보지 않는다.
- `DEC-NOTIFY`에서 정한 항목의 출처 원문이 바뀐 경우만 알린다.
- 수집 시각만 바뀐 경우와 정규화 규칙 변경으로 해석 결과만 바뀐 경우는 변경으로 알리지 않는다.
- 수집 실패나 일부 항목 미수집을 값이 사라진 변경으로 알리지 않는다.
- 알림에 어떤 항목이 어떻게 바뀌었는지 담는다.
- 같은 변경을 두 번 알리지 않는다. 수집을 재실행해도 같다.
- 발송·재시도·복구는 `REQ-NOTIFY-02`를 따른다.

P1:

- 띄어쓰기·문구 수정처럼 의미가 같은 원문 변경과 의미 있는 변경을 구분한다.
- 짧은 기간 안의 여러 변경을 묶어 한 번에 알린다.
- 출처에서 종료가 확인된 관심 혜택을 알린다. 종료 판단은 `REQ-SAVE-01` P1와 `DEC-DATA`를 따른다.

기한이 바뀐 경우 기한 알림 예약의 조정은 이 알림과 별개로 `REQ-NOTIFY-01`을 따른다.

## 전 단계 공통 품질 요구사항

### REQ-QUALITY-01 — 실패를 관찰하고 재현할 수 있는 운영

P0:

- 공공 API 오류와 DB 오류를 구분해 기록한다. 인증키·인증 토큰·전체 프로필은 로그에 남기지 않는다.
- 외부 호출에는 시간 제한과 재시도 상한을 둔다. 호출 제한·일시 장애·인증 실패를 같은 방식으로 무한 재시도하지 않는다.
- 수집 실행 한 번이 전체 API 한도를 소진하지 않도록 제한한다.
- 외부 장애·누락·중복·응답 유실 검증은 fake 또는 로컬 stub으로 재현하고, DB 제약은 실제 MySQL 테스트로 검증한다.

P1:

- 요청 또는 수집 실행 식별자로 원인을 추적할 수 있다.
- 사용자 조회 경로와 수집 작업을 구분해 지연·실패·DB 사용량을 측정할 수 있다.
- 수집/작업 실행이 겹쳤을 때의 처리 정책을 정하고 재현한다.

### REQ-QUALITY-02 — 캐시 사용 시 정확성

캐시를 도입할 때만 적용한다. 캐시 도입 자체가 P1이므로 아래 조건은 모두 P1이다.

P1:

- 사용자별 데이터가 공통 캐시를 통해 다른 사용자에게 전달되지 않는다.
- 정책 갱신·캐시 만료·캐시 장애 상황에 허용할 오래된 정보의 범위와 시간을 먼저 정한다. 수치는 측정 후 `DEC-FRESHNESS`에서 결정한다.
- 캐시가 꺼져 있거나 비어 있을 때도 기능이 동작한다. DB 처리 용량을 넘는 장애 부하는 대기·제한·오류 정책으로 다룬다.
- 갱신 전 조회가 늦게 끝나 오래된 값이 캐시에 다시 들어오는 상황을 재현하고, 선택한 정합성 기준을 만족하는지 검증한다.

성능 목표와 캐시 도입은 아직 확정하지 않았다. 검증 환경·트래픽 조건을 정하지 않은 임의의 처리량이나 응답시간을 완료 기준으로 사용하지 않는다.

### REQ-OPS-01 — 자동 검증과 배포

목적: 검증된 변경만 합쳐지고, 같은 절차로 반복해서 배포하고 되돌릴 수 있다.

P0:

- PR마다 `./gradlew test`를 자동으로 실행하고, 실패한 PR은 `develop`·`main`에 머지할 수 없다.
- 배포 산출물은 컨테이너 이미지로 만들고, 운영 이미지는 릴리스 태그 `vX.Y.Z`와 같은 버전으로 식별한다.
- 운영 배포는 릴리스 태그를 기준으로, 수동 서버 작업 없이 같은 절차로 반복할 수 있다.
- 배포 환경(서버·네트워크·DB)을 코드로 정의해 다시 만들 수 있다.
- 공공 API 인증키·DB 비밀번호는 이미지와 저장소에 넣지 않고 배포 환경의 비밀값으로 주입한다.
- 직전 릴리스 이미지로 되돌리는 절차가 있고, 실제로 실행해 검증했다.

P1:

- `develop`을 개발 환경에 자동으로 배포한다.
- 배포 중에도 요청이 실패하지 않는다. 구버전 앱과 새 스키마가 함께 동작하도록 마이그레이션을 확장과 축소 단계로 나눈다.
- 배포로 종료되는 수집·알림 작업이 처리 중인 작업을 잃지 않는다. 종료 대기와 `REQ-NOTIFY-02`의 복구로 검증한다.
- CI 소요 시간을 측정하고 줄인다.

배포 대상·환경 수·인프라 코드 도구는 `DEC-OPS`에서 정한다.

### REQ-OPS-02 — 운영 관측과 데이터 복구

목적: 운영 중 문제를 사용자보다 먼저 알고, 데이터를 잃어도 복구할 수 있다.

P0:

- 애플리케이션 상태 확인과 기본 지표(요청 지연·오류율, 수집 실행 결과)를 수집한다.
- 수집이 연속으로 실패하면 운영자에게 경보가 간다.
- 운영 DB를 정기적으로 백업하고, 백업 파일을 운영 서버 밖에 보관한다.

P1:

- 알림 발송 지연·실패율, 캐시 적중률 등 기능별 지표를 대시보드로 본다.
- 로그를 한곳에 모아 요청·수집 실행 식별자로 조회한다. `REQ-QUALITY-01` P1와 연결된다.
- 백업에서 실제로 복구해 보고, 복구 시간과 잃을 수 있는 데이터 범위를 측정한다.

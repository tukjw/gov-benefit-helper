# PR 생성

리뷰어가 변경 의도와 영향 범위를 빠르게 이해하고 검토할 수 있는 PR 초안을 작성합니다.

## GitHub 접근

- 이슈와 PR 조회·생성은 `gh`로 합니다. 저장소는 현재 디렉터리의 원격 주소로 자동 탐지하게 하고, 실패하면 사용자에게 `--repo <owner>/<repo>`를 확인합니다. 조회는 가능한 경우 `--json <필드>`를 사용합니다.
- 실제 PR 생성은 사용자가 명시적으로 요청한 경우에만 수행합니다. 생성 요청을 받았더라도 먼저 대상 저장소, 초안 전체(제목, 본문), base, head, push 필요 여부를 보여주고 사용자가 승인한 뒤에만 push와 생성을 실행합니다. 수정 요청을 받으면 반영한 초안을 다시 보여주고 다시 승인을 받습니다.
- 승인 후 소스 브랜치가 원격에 없거나 로컬 커밋이 원격보다 앞서 있으면 생성의 일부로 `git push -u origin <head>`를 먼저 실행합니다. force push는 하지 않으며, head가 `main`이나 `develop`이면 push하지 않고 멈춥니다. 그다음 본문을 임시 파일에 쓰고 `gh pr create --title "<제목>" --body-file <파일> --base <base> --head <head>`처럼 제목, 본문, 기준 브랜치와 소스 브랜치를 명시해 비대화형으로 실행합니다.
- 토큰을 명령 인자, PR 본문, 로그 또는 결과에 노출하지 않습니다. 인증·권한이 부족하면 자격 증명을 새로 만들거나 권한을 우회하지 말고 보고합니다.
- 생성 후 출력된 PR URL과 번호, 적용된 제목, 기준 브랜치, 소스 브랜치를 확인해 결과로 알립니다.

## 변경 범위 확정

- 기준 브랜치는 저장소 지침의 분기 규칙에 따라 정합니다.
- `git fetch origin <base>`로 기준 브랜치를 갱신한 뒤 `git log origin/<base>..HEAD`와 `git diff origin/<base>...HEAD`를 기준으로 변경을 파악합니다. 작업 브랜치는 PR을 올리는 시점에 push하는 것이 정상이므로, 소스 브랜치가 원격에 없거나 로컬이 원격보다 앞서 있어도 문제로 알리지 않습니다.
- 미커밋 변경은 초안에 반영하지 않습니다. PR 생성 요청이면 미커밋 변경이 있는 동안 생성하지 않고 이유를 보고합니다.
- 초안만 요청받았을 때는 `git push`하지 않습니다.
- 이슈에 대응하는 플랜 파일(`docs/plans/<이슈번호>-*.md`)의 `status`가 `done`이 아니면 알립니다. PR 생성 요청이면 생성하지 않고 멈춥니다. 플랜 파일을 직접 수정하거나 커밋하지 않습니다.

## 작성 원칙

- 관련 지침, 변경 내역, 커밋을 먼저 확인하고 확인된 사실을 기준으로 작성합니다.
- 사용자가 제공했거나 저장소에서 확인한 사실만 사용합니다. 변경 이유, 테스트 결과, 이슈 번호를 임의로 만들지 않습니다.
- 제목은 저장소 지침의 커밋 메시지 형식을 따릅니다. squash 머지 시 PR 제목이 그대로 커밋 메시지가 됩니다. 예: `feat: 회원가입 이메일 중복 검증 추가 (#42)`.
- `변경 내용`은 diff를 열지 않아도 무엇이 어떻게 바뀌었는지 알 수 있게 씁니다. 기능·동작·구조 단위로 주요 변경을 빠짐없이 적고, 파일 경로, 클래스명, 설정 키, 삭제 목록 같은 나열은 리뷰어가 diff만으로 찾기 어려운 경우에만 적습니다.
- 호출의 순서나 경로 자체가 변경의 핵심일 때만 `변경 내용`에 다이어그램을 넣습니다. 동시 요청의 경합, 인증 핸드셰이크, 요청 경로 이동처럼 "누가 누구를 어떤 순서로 부르는가"를 문장으로 쓰면 여러 문장이 필요한 경우가 대상입니다. 새 API나 화면 추가처럼 참여자가 많아도 흐름이 평범하면 넣지 않습니다. 호출 흐름은 `mermaid` `sequenceDiagram`, 한 방향 데이터 파이프라인은 `flowchart`를 씁니다. 참여자 5개·메시지 10개 정도를 권장 크기로 하고, 변경 전 흐름은 Note 한 줄로 둡니다. 다이어그램이 있으면 같은 흐름을 문장으로 반복하지 않습니다.
- `변경 이유`에는 해결하려는 문제와 이 방식을 택한 이유를 씁니다. 검토했다가 택하지 않은 방안이 있을 때만 `검토한 방안` 목록으로 방안과 제외 이유를 적습니다.
- `테스트 방법 / 결과`에는 수행한 명령이나 검증한 케이스와 결과를 적습니다. 긴 로그 인용과 출력·헤더 나열은 생략하되, 변경 효과를 입증하는 수치와 관찰 결과는 간결하게 포함합니다.
- 테스트는 직접 실행하지 않습니다. 이번 작업에서 실행했거나 사용자가 제공한 결과만 적고, 변경된 디렉터리에 해당하는 저장소 검증 명령 중 결과가 없는 것은 `미실행`으로 표시합니다. 실행하지 않은 테스트를 통과했다고 표현하지 않습니다.
- `관련 이슈`에서 이 PR이 병합될 때 이슈를 닫아야 하면 `Closes #123`, 연결만 필요하면 `Related to #123`을 사용합니다. 플랜 파일이 있으면 경로를 함께 적습니다.
- `리뷰 포인트`에는 리뷰어의 판단이 필요한 항목을 적습니다. 결정 과정의 이력, 향후 대비 메모, 이미 결정된 사항의 해설은 플랜 파일로 보냅니다.
- 섹션 간 반복을 줄이고, 변경 규모에 맞는 분량으로 씁니다. 필요한 내용이면 길어도 되지만, diff나 플랜에 이미 있는 내용을 채우기 위해 늘리지 않습니다.
- 누락된 정보가 PR 내용의 정확성을 크게 바꾼다면 꼭 필요한 질문만 간결하게 합니다. 그렇지 않으면 초안을 작성하고 불확실한 부분을 `확인 필요`로 표시합니다.
- 기본적으로 PR 초안만 작성합니다. 외부 저장소에 PR을 실제로 생성하거나 게시하는 작업은 사용자가 명시적으로 요청하고 필요한 도구를 사용할 수 있을 때만 수행합니다.

## 출력 형식

다음 구조를 사용자의 언어로 작성합니다. 사용자가 요청하거나 모호함을 방지하는 데 꼭 필요한 경우가 아니라면 섹션을 추가하지 않습니다.

```markdown
제목: <type>: <변경 핵심을 담은 한 줄> (#<이슈번호>)

## 변경 내용

- <추가하거나 수정한 기능 또는 코드>
- <주요 변경사항>

## 변경 이유

<변경이 필요한 이유와 해결하려는 문제 또는 요구사항>

검토한 방안: (해당할 때만)
- <택하지 않은 방안>: <제외 이유 한 줄>

## 테스트 방법 / 결과

- <테스트 명령 또는 검증 케이스>: <통과, 실패, 미실행과 그 이유>

## 관련 이슈

- <Closes #123 또는 Related to #123, 없으면 없음>
- 플랜: <docs/plans/<이슈번호>-<슬러그>.md> (있을 때만)

## 리뷰 포인트

- <리뷰어 판단이 필요한 사항, 없으면 특이사항 없음>
```

# PR 리뷰

변경이 이슈와 플랜대로 이루어졌는지, 저장소 규칙을 지켰는지, 실제로 수정할 가치가 있는 결함이 있는지를 근거와 함께 보고합니다. 리뷰 결과는 출력만 하며 GitHub에 승인, 거절, 댓글을 게시하지 않습니다.

## GitHub 접근

- PR 조회는 `gh`로 합니다. 저장소는 현재 디렉터리의 원격 주소로 자동 탐지하게 하고, 실패하면 사용자에게 `--repo <owner>/<repo>`를 확인합니다. `gh pr view <PR 번호> --json number,title,body,baseRefName,headRefName,headRefOid,labels,comments,reviews`와 `gh api repos/{owner}/{repo}/pulls/<PR 번호>/comments`로 메타데이터, 일반 댓글, 리뷰, 코드 라인 댓글을 읽습니다.
- 토큰을 명령 인자, 리뷰 내용, 로그 또는 결과에 노출하지 않습니다. 인증·권한이 부족하면 자격 증명을 새로 만들거나 권한을 우회하지 말고 보고합니다.

## 검토 범위 확정

- PR 번호를 받으면 base와 head 브랜치를 확인하고, `git fetch origin <base> <head>` 후 `git log origin/<base>..origin/<head>`와 `git diff origin/<base>...origin/<head>`를 리뷰 대상으로 삼습니다. PR에 실제로 들어가는 것은 원격 head이므로 로컬 HEAD를 기준으로 쓰지 않습니다.
- 로컬 head 브랜치에 원격에 푸시되지 않은 커밋이나 미커밋 변경이 있으면 리뷰 대상이 아니라고 알립니다.
- 브랜치나 커밋 범위를 받으면 그 범위를, 대상 지정이 없으면 현재 작업 트리와 스테이징 변경을 검토합니다.
- 결과 첫 줄에 검토한 PR 번호, base, head 커밋을 적어 어떤 상태를 리뷰했는지 남깁니다.

## 플랜 대조

- PR 제목이나 본문의 이슈 번호로 `docs/plans/<이슈번호>-*.md`를 찾아 읽습니다. 플랜이 없으면 그 사실을 알리고 이슈 본문의 완료 조건만으로 대조합니다.
- 플랜 `status`가 `done`이 아니면 알립니다.
- 플랜의 `완료 조건 매핑` 각 항목이 변경으로 충족되는지 확인하고, 충족되지 않은 항목은 `필수 수정`으로 보고합니다.
- 플랜의 `포함`·`제외` 범위 밖 변경과, `설계 결정`과 다른 구현은 저장소 지침이 금지하는 범위 확장이므로 지적합니다. 플랜에 `결정 필요`가 남아 있는데 구현이 한쪽을 택했다면 확인 질문으로 남깁니다.

## 저장소 규칙 점검

- PR base가 분기 규칙과 맞는지 확인합니다. 일반 이슈·hotfix 역머지·릴리스 버전 반영은 `develop`, hotfix는 `main`, 릴리스는 `develop → main`입니다.
- PR 제목이 `<type>: <한국어 요약> (#<이슈번호>)` 형식이고 `type`이 이슈 라벨과 맞는지 확인합니다. 릴리스 버전 반영 PR은 `release: vX.Y.Z 버전 반영`이고, 릴리스 PR은 `release: vX.Y.Z`입니다. 두 PR 모두 저장소 지침의 릴리스 절에 적힌 버전 파일이 `X.Y.Z`여야 합니다.
- `.env` 내용, DB 자격 증명, API 키가 코드나 문서에 새로 하드코딩되지 않았는지 확인합니다. 저장소 지침이 예외로 둔 로컬 전용 기본 계정은 제외합니다. 발견하면 `높음`으로 보고합니다.
- 새 테스트가 저장소 지침의 검증 절을 따르는지 확인합니다. 외부 서비스에 의존하는 테스트, DB가 필요한데 Testcontainers MySQL 대신 대체 DB를 쓰는 테스트, 실제 외부 API에 요청하면서 기본 실행에 포함된 테스트를 지적합니다.

## 결함 검토

- 변경으로 새로 발생하거나 변경 때문에 영향을 받는 문제를 우선합니다. 변경과 무관한 기존 문제는 이번 변경이 위험을 키우지 않는 한 보고하지 않습니다.
- 수정된 코드의 호출부, 설정, 스키마, 테스트를 필요한 범위에서 함께 읽습니다. 재현 조건이나 구체적인 실패 가능성이 있는 문제만 지적하고, 취향 차이와 포매터가 처리할 스타일은 제외합니다.
- 기존 리뷰 댓글에서 이미 지적된 항목은 반복하지 않고 해결 여부만 확인합니다.
- 같은 원인에서 나온 문제는 하나로 묶고 심각도 순으로 정렬합니다. `높음`은 보안, 데이터 손상, 주요 기능 장애나 회귀, `보통`은 특정 조건의 오류나 중요한 테스트 누락, `낮음`은 병합을 막지 않는 품질 문제입니다.

## 검증 명령 실행

- 저장소 지침의 검증 절에서 변경된 디렉터리에 해당하는 명령을 실행합니다. 실제 외부 API에 요청하도록 분리된 테스트는 실행하지 않습니다.
- 로컬 HEAD가 원격 head 커밋과 같을 때만 실행합니다. 다르면 브랜치를 전환하지 말고 `미실행`으로 표시하고, 필요하면 `scripts/worktree.sh`로 별도 워크트리를 만들어 실행할 수 있다고 안내합니다.
- 실행한 명령과 결과를 그대로 적고, 실행하지 않은 테스트를 통과했다고 표현하지 않습니다.

## 출력 형식

지적 사항을 가장 먼저 제시합니다. 비어 있는 하위 섹션은 생략하며, 문제가 없으면 `수정이 필요한 문제를 발견하지 못했습니다.`라고 명시합니다.

```markdown
## 리뷰 결과

검토 범위: PR #<번호>, `<base>` ← `<head>` (`<head 커밋>`)

### 필수 수정

- [높음 또는 보통] <문제의 핵심>
  - 위치: `경로/파일:라인`
  - 문제: <발생 조건과 잘못된 동작>
  - 영향: <오류, 회귀, 보안 또는 데이터 영향>
  - 제안: <수정 방향>

### 권장 수정

- [보통 또는 낮음] <문제의 핵심>
  - 위치: `경로/파일:라인`
  - 이유: <구체적인 위험>
  - 제안: <개선 방향>

### 확인 질문

- <구현 의도나 요구사항 확인이 필요한 내용>

## 플랜·규칙 대조

- 완료 조건: <모두 충족 또는 미충족 항목>
- 범위·설계 결정: <플랜과 일치 또는 벗어난 변경>
- 저장소 규칙: <base, 제목, 자격 증명, 테스트 격리 확인 결과>

## 테스트 검토

- 실행 결과: <실행한 명령과 통과, 실패 또는 미실행과 이유>
- 누락된 테스트: <필요한 테스트 또는 없음>

## 최종 의견

<승인 가능, 수정 후 재검토 또는 병합 차단과 짧은 근거>
```

- `승인 가능`: 병합을 막을 문제가 없음
- `수정 후 재검토`: 수정해야 할 구체적인 문제가 있음
- `병합 차단`: `높음` 문제가 있거나 완료 조건이 충족되지 않아 현재 상태로 병합하면 안 됨

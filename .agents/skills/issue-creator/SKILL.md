# 이슈 생성

팀원이 불필요한 해석 없이 이해하고 작업할 수 있는 이슈 초안을 작성합니다.

## GitHub 접근

- 이슈, 라벨, 마일스톤 조회와 이슈 생성은 `gh`로 합니다. 저장소는 현재 디렉터리의 원격 주소로 자동 탐지하게 하고, 실패하면 사용자에게 `--repo <owner>/<repo>`를 확인합니다. 조회는 가능한 경우 `--json <필드>`를 사용합니다.
- 토큰을 명령 인자, 이슈 본문, 로그 또는 결과에 노출하지 않습니다. 인증·권한이 부족하면 자격 증명을 새로 만들거나 권한을 우회하지 말고 보고합니다.
- 조회는 초안 작성에 필요한 범위에서 수행할 수 있습니다. 실제 이슈 생성과 그 밖의 GitHub 변경은 사용자가 명시적으로 요청한 경우에만 수행합니다.

## 실제 이슈 생성 절차

사용자가 GitHub 이슈 생성을 명시적으로 요청했을 때만 수행합니다. 생성 요청을 받았더라도 초안을 먼저 보여주고 사용자가 승인한 뒤에만 생성합니다.

1. `gh issue list --state open --limit 100 --json number,title,labels`로 열린 이슈를 조회해 같은 주제의 이슈가 있으면 생성하지 않고 후보를 알립니다. 사용자가 그래도 생성하라고 하면 진행합니다.
2. `gh label list --limit 100 --json name`으로 기존 라벨을 조회해 선택한 라벨 이름이 정확히 일치하는지 확인합니다. 존재하지 않는 라벨은 사용자가 명시적으로 요청하지 않는 한 새로 만들지 않습니다.
3. 추천 마일스톤이 있으면 `gh api 'repos/{owner}/{repo}/milestones?state=open' --jq '.[].title'`로 열린 마일스톤을 조회해 이름이 정확히 일치하는지 확인합니다. 없으면 마일스톤을 새로 만들지 않고, 추천한 마일스톤이 GitHub에 없다는 사실을 사용자에게 알린 뒤 초안의 마일스톤을 `없음`으로 바꿉니다.
4. 대상 저장소, 초안 전체(제목, 본문, 라벨, 마일스톤), 생성할 로컬 브랜치 이름(`<type>/<이슈번호>-<슬러그>`)과 분기 원점을 보여주고 생성 여부를 묻습니다. 초안에 `확인 필요`가 남아 있으면 이때 함께 알립니다. 사용자가 승인하기 전에는 이슈와 브랜치를 생성하지 않습니다. 수정 요청을 받으면 반영한 초안을 다시 보여주고 다시 승인을 받습니다.
5. 사용자가 `확인 필요`가 남은 채로 승인하면 `확인 필요` 항목을 본문에 유지하고 `status/needs-info` 라벨을 함께 붙입니다.
6. 승인된 초안의 `제목:` 줄은 `--title`로, `추천 라벨` 섹션은 `--label`로, `추천 마일스톤`이 `없음`이 아니면 `--milestone`으로 넘기고, 본문에는 `배경 / 문제 상황`, `작업 내용`, `완료 조건` 섹션만 넣습니다. 본문은 임시 파일에 쓰고 `gh issue create --title "<제목>" --body-file <파일> --label "<라벨1>,<라벨2>" --milestone "<마일스톤>"`처럼 비대화형으로 실행합니다. 여러 줄 마크다운을 명령 인자에 직접 넣지 않습니다.
7. 실행 후 출력된 이슈 URL에서 이슈 번호를 확인합니다.

## 작성 원칙

- 사용자가 제공한 사실, 용어, 의도한 범위를 유지합니다. 원인, 요구사항, 기술적 결정을 임의로 만들지 않습니다.
- 제목은 핵심 변경 사항이나 기대 결과가 드러나는 한 줄로 작성합니다. `로그인 실패 시 에러 메시지 개선`처럼 행동 중심의 표현을 우선합니다. 이슈 제목이 커밋과 PR 제목(`<type>: <요약> (#<이슈번호>)`)의 요약부로 쓰일 수 있도록 그 자리에 들어가도 자연스러운 문장으로 씁니다.
- `배경 / 문제 상황`에는 현재 발생하는 문제와 이 작업이 필요한 이유를 설명합니다.
- `작업 내용`에는 실제로 변경하거나 구현할 사항을 결과 수준에서 짧게 적습니다. 테이블 스키마, 라이브러리, 어노테이션, 클래스 이름 같은 구현 세부는 대화에서 논의되었더라도 이슈에 적지 않고 `docs/plans/`의 플랜으로 넘깁니다. 사용자가 이슈에 명시하라고 요청한 경우에만 예외로 합니다.
- 구현 방식에 대한 `결정 필요` 항목은 이슈에 나열하지 않고 플랜 작성 단계로 넘깁니다. 작업 범위 자체를 가르는 결정만 `확인 필요`로 남깁니다.
- `완료 조건`은 관찰하고 검증할 수 있는 체크리스트로 작성합니다. 입력 내용에 근거가 있다면 성공, 실패, 경계 상황을 포함합니다. `./gradlew test`처럼 저장소 지침의 검증 절에 이미 있는 공통 검증 명령은 완료 조건에 반복하지 않고 이 이슈 고유의 조건만 적습니다.
- `추천 라벨`에는 아래 라벨 목록에서 이슈에 맞는 항목만 선택합니다. 라벨을 임의로 만들지 않습니다.
- `추천 마일스톤`은 아래 마일스톤 규칙에 따라 하나를 고르거나 `없음`으로 적습니다.
- 섹션 간 반복을 제거하고, 이슈의 복잡도에 맞는 짧은 문단과 목록을 사용합니다.
- 누락된 정보가 작업 범위나 완료 조건을 크게 바꾼다면 꼭 필요한 질문만 간결하게 합니다. 그렇지 않으면 유용한 초안을 먼저 작성하고 불확실한 부분을 `확인 필요`로 표시합니다.

## 라벨 규칙

아래 목록은 GitHub 저장소의 라벨과 같아야 합니다. GitHub 라벨이 바뀌면 이 목록도 갱신합니다.

유형은 정확히 하나를 선택합니다.

- `type/bug`
- `type/hotfix`
- `type/feature`
- `type/improvement`
- `type/refactor`
- `type/docs`
- `type/test`
- `type/chore`

`type/hotfix`는 저장소 지침의 hotfix 판단 기준을 따릅니다. 배포된 `main`의 긴급 결함이고 `develop`에 쌓인 변경을 함께 배포할 수 없을 때만 선택하며, 그 외의 결함은 `type/bug`로 둡니다.

영향받는 영역을 식별할 수 있으면 하나 이상 선택합니다.

- `area/backend`
- `area/frontend`
- `area/worker`
- `area/infra`

우선순위가 명확할 때만 하나를 선택합니다. `docs/product/requirements.md`의 P0·P1과 같은 기준입니다.

- `priority/p0`: 기능이 끝까지 동작하는 데 필요한 작업
- `priority/p1`: P0 완성 후 다룰 후속 작업
- `priority/p2`: 아이디어·언젠가 할 작업

작업이 막혔거나 추가 정보가 필요한 경우에만 상태를 선택합니다.

- `status/blocked`
- `status/needs-info`

## 마일스톤 규칙

아래 목록은 GitHub 저장소의 마일스톤과 같아야 하며, `docs/product/overview.md`의 기능 단계에 대응합니다. GitHub 마일스톤이 바뀌면 이 목록도 갱신합니다.

- `1차 탐색`: `docs/product/requirements.md`의 1차 요구사항(`REQ-DATA-*`, `REQ-SEARCH-*`, `REQ-DETAIL-*`)
- `2차 개인화 MVP`: 2차 요구사항(`REQ-ACCOUNT-*`, `REQ-PROFILE-*`, `REQ-MATCH-*`, `REQ-SAVE-*`)
- `3차 알림`: 3차 요구사항(`REQ-NOTIFY-*`)

마일스톤은 다음 기준으로 정합니다.

- `priority/p0` 이슈는 관련 요구사항이 속한 단계의 마일스톤 하나를 추천합니다.
- 다음 이슈는 `없음`으로 둡니다: `priority/p1`·`priority/p2` 이슈, 우선순위 라벨이 없는 이슈, 운영 작업(O1~O4), 전 단계 공통 요구사항(`REQ-QUALITY-*`, `REQ-OPS-*`)만 다루는 이슈, 저장소 도구·지침 작업, 관련 요구사항이 여러 단계에 걸치거나 단계를 판단하기 어려운 이슈.
- 이미 있는 마일스톤 중에서만 고르고, 마일스톤을 새로 만들지 않습니다.

## 로컬 브랜치 생성 규칙

GitHub 이슈 생성이 성공하면 해당 저장소에 로컬 브랜치도 생성합니다.

- 브랜치 이름은 저장소 지침의 `<type>/<이슈번호>-<슬러그>` 형식을 따릅니다. `type`은 유형 라벨에 대응합니다: `type/bug` → `fix`, `type/hotfix` → `hotfix`, `type/feature` → `feat`, `type/improvement` → `improve`, `type/refactor` → `refactor`, `type/docs` → `docs`, `type/test` → `test`, `type/chore` → `chore`.
- 슬러그는 이슈 제목을 요약한 짧은 영문 kebab-case로 항상 만듭니다. 이 슬러그가 플랜 파일명 `docs/plans/<이슈번호>-<슬러그>.md`를 정하므로 생략하지 않습니다.
- 분기 원점은 저장소 지침의 분기 규칙을 따릅니다. 일반 이슈는 `develop`, `type/hotfix`는 `main`입니다.
- 생성 직전에 `git fetch origin <분기 원점>`으로 원격 추적 브랜치를 갱신하고, `git branch --no-track <브랜치 이름> origin/<분기 원점>`과 동등한 명령으로 원격 상태에서 분기합니다. `--no-track`을 빼면 새 브랜치의 upstream이 `origin/<분기 원점>`으로 잡혀 이후 `git pull`과 `git status`가 분기 원점을 기준으로 동작하므로 반드시 붙입니다. 로컬 `develop`이나 `main`이 뒤처져 있어도 그 상태에서 분기하지 않습니다. 생성한 브랜치로 전환하지 않습니다.
- fetch가 실패하거나 원격에 분기 원점이 없으면 로컬 브랜치나 다른 시작점을 추측하지 말고 브랜치를 생성하지 않은 채 이유를 보고합니다.
- 현재 작업 트리가 변경된 상태여도 브랜치 생성만 수행할 수 있으므로 이를 이유로 중단하지 않습니다.
- 같은 이름의 로컬 브랜치가 이미 있으면 덮어쓰거나 다른 이름을 임의로 만들지 말고 기존 브랜치가 있음을 보고합니다.
- `git pull`, `git push`를 실행하지 않으며 원격 브랜치를 생성하지 않습니다.
- 이슈 생성 후 브랜치 생성이 실패해도 생성된 이슈를 삭제하지 않습니다. 이슈 번호와 브랜치 실패 원인을 함께 보고합니다.

## 출력 형식

다음 구조를 사용자의 언어로 작성합니다. 사용자가 요청하거나 모호함을 방지하는 데 꼭 필요한 경우가 아니라면 섹션을 추가하지 않습니다.

```markdown
제목: <한 줄로 핵심>

## 배경 / 문제 상황

<현재 어떤 문제가 있는지와 왜 이 작업이 필요한지>

## 작업 내용

- <실제로 변경하거나 구현할 내용>

## 완료 조건 (Acceptance Criteria)

- [ ] <이슈를 닫을 수 있는 검증 가능한 조건>

## 추천 라벨

- `<type/...>`
- `<area/...>`
- `<필요한 경우 priority/... 또는 status/...>`

## 추천 마일스톤

- `<마일스톤 이름>` 또는 `없음`
```

GitHub 이슈와 로컬 브랜치를 실제로 생성했다면 이슈 본문과 분리해 다음을 결과로 알립니다.

- 이슈 번호 또는 URL과 적용한 라벨, 지정한 마일스톤
- 생성한 로컬 브랜치 이름과 분기 원점(`origin/develop` 또는 `origin/main`), 브랜치를 전환하지 않았다는 사실
- 대응하는 플랜 파일 경로 `docs/plans/<이슈번호>-<슬러그>.md` (작성 예정)
